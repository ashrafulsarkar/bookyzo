### 1.3 `wp_byzo_slots` — generated bookable time slots (materialized, not computed on the fly)
| Column | Type | Notes |
|---|---|---|
| id | BIGINT UNSIGNED PK | |
| bookable_item_id | BIGINT UNSIGNED | FK |
| start_datetime | DATETIME | stored in site-local time (WordPress site timezone — see §5 item 1) |
| end_datetime | DATETIME | |
| capacity_remaining | SMALLINT UNSIGNED | decremented on booking, for capacity>1 bookable items |
| status | VARCHAR(20) | `open`, `full`, `blocked` |

Generated by a background cron (`byzo_generate_slots` scheduled event) on a **rolling window** — e.g. always keep the next `max_advance_days` of slots materialized, regenerate nightly. Reason to materialize rather than compute on the fly: booking a slot must atomically decrement `capacity_remaining` (race-condition safety on concurrent bookings), which needs a real row to lock/update.

**Event-type bookable items bypass the generator entirely (decided 2026-09-02, §5 item 7).** An event is one or more *specific dated occurrences* ("Oct 15, 7pm, 100 seats"), not a weekly recurring pattern — so for `type = event` bookable items: no `wp_byzo_schedules` rows, no Availability/Exceptions tabs; the admin enters occurrences directly (a "Dates" tab on the bookable item form), and each occurrence is written **straight into `wp_byzo_slots`** (`start_datetime`/`end_datetime` per occurrence, `capacity_remaining` seeded from `bookable_item.capacity`). `BYZO_Slot_Generator` must skip `type = event` bookable items (both the nightly cron and the regenerate-on-save triggers — otherwise cleanup_future_open_slots-style logic could delete manually entered occurrences). Zero schema change needed: the materialized-slots model already fits one-off occurrences perfectly; booking, capacity decrement, and the public `/slots` read all work unchanged. **Built 2026-09-03 (ROADMAP.md Phase 1.5 step 5)**: `BYZO_Slot::create_occurrence()`/`delete_occurrence()`/`list_for_bookable_item()`, admin REST routes `GET/POST /bookable-items/{id}/slots` + `DELETE .../slots/{slot_id}` (§4), `BYZO_Slot_Generator::generate_for_bookable_item()`'s single early-return for `type = event`, and the "Dates" tab (`BookableItemDatesTab.vue`) replacing Availability/Exceptions on the bookable item edit screen for event items.

### 1.5 `wp_byzo_customers` — customer identity (DONE 2026-09-05 — Phase 1.5 step 9; speced 2026-09-03, competitor gap-fill A10/B3)

Free-owned table (created by Free's own `dbDelta` activator, not gated to Pro) — needed because "import an existing customer list from CSV" (A10) requires a customer to exist independently of any booking, which the previous booking-only model couldn't represent.

| Column | Type | Notes |
|---|---|---|
| id | BIGINT UNSIGNED PK | |
| name | VARCHAR(255) | |
| email | VARCHAR(255) | unique index — the natural key for upsert-on-booking and CSV import de-duplication |
| phone | VARCHAR(50) NULL | |
| notes | TEXT NULL | |
| tags | VARCHAR(255) NULL | comma-separated, admin-curated (e.g. `vip, regular`) — shown as a column in the Customers list and settable from the customer form. Unlike the bookable-item tags dropped in §1.1, these have a consumer and a list long enough to need them. |
| source | VARCHAR(20) | `booking` (auto-created the first time this email books) or `import` (created via A10's CSV import with no booking yet) |
| wp_user_id | BIGINT UNSIGNED NULL | added 2026-09-06 (`FEATURES.md` A11, customer accounts/dashboard) — links this customer record to a real WP account once they register (a new, zero-capability `byzo_customer` role, never wp-admin access); NULL for a customer who has only ever booked as a guest. Unique when not null — one WP account maps to at most one customer row; MySQL's `UNIQUE` index permits multiple NULLs, so guest-only rows are unaffected. Registering with an email that already has a guest-created row here (via booking upsert, below) links to that existing row rather than creating a duplicate — the account immediately sees its full prior booking history. |
| created_at, updated_at | DATETIME | |

**Booking creation upserts this table by email**: on `POST /bookings`, look up `wp_byzo_customers` by `customer_email`; if found, set `bookings.customer_id` to it (and refresh `name`/`phone` if changed — the customer record tracks their *current* details, the booking row keeps what was true *then*); if not found, insert a new customer row with `source = 'booking'`. CSV import (A10) inserts rows with `source = 'import'` directly, no booking involved. This table is what B3's "customer booking history and profile" and B3's "export customer list to CSV, including booking and payment history" (added 2026-09-03) actually query — `JOIN wp_byzo_bookings ON customer_id`.

### A4. Booking management (admin)
- Calendar view: day/week/month toggle — Vue component consuming `GET /wp-json/bookyzo/v1/bookings?from=&to=&bookable_item_id=`
- Manual booking creation modal (for phone/walk-in) — same REST endpoint as the public widget uses (`POST /wp-json/bookyzo/v1/bookings`), just called from wp-admin context with `current_user_can` check instead of guest flow
- Status transitions: pending→confirmed→completed, or →cancelled/no_show at any point before completed. Enforce valid transitions server-side (a state machine table, not free-form status writes) — prevents e.g. "completed" flipping back to "pending" by a stray API call
- **`rejected` status (added 2026-09-05, Phase 1.6):** a new terminal transition, `pending → rejected` only (a `confirmed` booking can't be "rejected," only cancelled — rejection is specifically an admin declining a request before ever accepting it). Kept out of `TRANSITIONS`' other branches deliberately — same state-machine-table enforcement as every other transition, not a free-form status write.
- **Basic reschedule (added 2026-09-05, Phase 1.6):** `BYZO_Booking::reschedule( $id, $new_slot_id )` — not a status transition, a `slot_id` change. Atomically releases the old slot's `capacity_remaining` and claims the new slot's (same conditional-`UPDATE` pattern Phase 0's booking creation already uses, applied twice in one transaction), sets `rescheduled_at`, leaves `status` untouched. Available from `pending` or `confirmed` only — rescheduling a `completed`/`cancelled`/`no_show`/`rejected` booking makes no sense and is rejected with the same `byzo_invalid_transition`-style error the status state machine already uses.
- **Auto-confirm (added 2026-09-03, built same day — Phase 1.5 step 6):** `BYZO_Booking::create()` reads `byzo_settings.auto_confirm` (default `false`) — when `true`, the row is inserted with `status = 'confirmed'` directly instead of `'pending'`. `byzo_booking_created` still fires unconditionally either way (unchanged); `BYZO_Notifications::on_booking_created()` is what actually adapts, checking the booking's real resulting status to send the `booking_confirmed` template instead of `booking_created` when it's already confirmed — simpler than introducing a second action name for the same outcome, and avoids the customer getting both a "request received" and a "confirmed" email back to back. The `TRANSITIONS` state machine itself is unchanged — this only picks the *starting* state, capacity-decrement/payment logic is identical either way.
- **Single cancellation policy (DONE 2026-09-05 — Phase 1.5 step 7):** one fixed time-limit rule in `byzo_settings.cancellation_hours` (default `24`, `0` = no guest cancellation), validated in `BYZO_Settings::update()`. Consumed by `BYZO_Booking::cancel_via_token( $id, $token )` — checks token validity (`BYZO_Booking_Token::verify()`), a valid pending/confirmed→cancelled transition, `cancellation_hours > 0`, and `slot_start − now > cancellation_hours`, in that order, each with its own error code (`byzo_invalid_token`/`byzo_invalid_transition`/`byzo_cancellation_disabled`/`byzo_cannot_cancel`/`byzo_cancellation_window_passed`). **Not a REST route** — reached via `BYZO_Booking_Cancel`, an `admin_post_nopriv_byzo_cancel_booking`/`admin_post_byzo_cancel_booking` handler (the WordPress-idiomatic guest-write pattern, matching `BYZO_Booking_Export`'s existing `admin-post.php` precedent, chosen over building new REST+CORS plumbing for a guest that has no nonce). `template_redirect` intercepts a `?byzo_manage_booking=1` query var and renders `templates/manage-booking.php` (a standalone page bypassing the active theme entirely) via `BYZO_Booking_Cancel::render()` — made a public static method deliberately, mirroring `BYZO_Booking_Export::stream_csv()`'s I/O/logic split, so a CLI smoke test can exercise its confirm/cancelled/error page-state logic directly without forking a process. Admin cancellation (`BYZO_Booking::update_status()`) stays completely unrestricted by this policy. Multiple policy tiers remain Pro (B3).

- Widget copy must be type-aware generally — no hardcoded "appointment" wording in steps/confirmation once four types are live. **DONE 2026-09-11**: `src/widget/copy.js` holds one map of per-type wording (heading, sub, submit/submitting label, confirmation heading, subject label, quantity label, remaining/sold-out phrasing) that every step looks up via `copyFor(type)` — one table rather than `type === 'x'` conditionals spread across five components, so a fifth type is a new row rather than an audit. `appointment` doubles as the fallback so a missing/unknown type can never render `undefined`. Raising the party size after choosing a time clears that choice rather than letting Continue submit a slot that no longer qualifies. The chosen size rides along on the `selected` event to `StepDetails`, which then shows it as a settled summary row instead of asking again. Every other type keeps asking on the details step, where quantity doesn't change which slots are bookable.
- **Widget UI redesign (DONE 2026-09-10):** the slot step moved from a flat run of date chips to a real **month calendar grid** (`StepSlot.vue`) — with a 30-day booking window the old list rendered ~26 undifferentiated chips with no sense of week, weekend, or month boundary. Only months containing availability are reachable via the arrows, and only days with slots are actionable (other days stay visible for orientation but are not targets). Times below are grouped **Morning / Afternoon / Evening** rather than one flat row, and picking a time no longer auto-advances — a **Continue** button confirms, matching every other step and letting the visitor change their mind. `StepDetails.vue` and `StepConfirmation.vue` gained a shared **summary card** (service / when / where) so the chosen slot is never out of sight while filling the form, which is the most common abandonment point. All of it is still driven by the same `--byzo-*` tokens, so the Appearance settings above continue to control the new elements with no extra wiring. **Event-type items skip the calendar entirely** (added 2026-09-10): an event is a handful of specific dated occurrences the admin entered by hand (§1.3), not a recurring pattern, so there is no "pick a day, then a time within it" to perform — a month grid would mean navigating mostly-empty months for what is usually three or four dates. Events instead list their occurrences directly as selectable cards (date, time, and seats remaining), the heading reads "Choose a date" rather than "Pick a time", and a sold-out occurrence stays listed but disabled rather than vanishing. Same Continue-to-confirm behavior as the calendar path.
- **Appearance settings (DONE 2026-09-10):** `BYZO_Appearance_Settings` (option `byzo_appearance`, REST `/appearance`) + an Appearance admin screen (`/settings/appearance`, `AppearanceSettings.vue` with a live `WidgetPreview.vue`). ### A6. Notifications
- Transactional emails via `wp_mail()`, templates as PHP files in `templates/emails/` overridable via theme (same `byzo_get_template()` pattern as CBFW's `cbfw_get_template()`)
- Events: `byzo_booking_created`, `byzo_booking_confirmed`, `byzo_booking_cancelled`, `byzo_booking_reminder` (fired by a cron scanning for bookings starting in exactly 24h, matched to the hour to avoid duplicate sends — store `reminder_sent_at` on the booking row)

- **Notification toggles (added 2026-09-03, built same day — Phase 1.5 step 6):** `byzo_settings.send_confirmation_email` and `byzo_settings.send_admin_notification` (both default `true`) gate `BYZO_Notifications`' sends independently. `send_confirmation_email` gates the two customer-facing "you're booked" templates (`booking_created`, `booking_confirmed` — not `booking_cancelled`/`booking_reminder`, which stay unconditional). `send_admin_notification` gates a new 5th event, `admin_new_booking` (added to `BYZO_Email_Templates::EVENTS`, same plain-text-editable shape as the other 4), sent to `get_option('admin_email')` — no per-plugin override field for the admin address was built, matching what's actually in `byzo_settings` today. Both toggles fire independently of each other on every new booking (`BYZO_Notifications::on_booking_created()`), regardless of `auto_confirm`'s effect on which customer template gets picked. Neither is B5's "real-time alerts," which stays an in-admin-UI Pro feature layered on top.
- **"Add to calendar" link (DONE 2026-09-05 — Phase 1.5 step 9; moved to Free 2026-09-03 per the same-day `FEATURES.md` tier reassignment):** computed on the fly, not stored, from the booking's own `slot_start`/`slot_end`/bookable item name. Two distinct implementations, not one shared code path (JS and PHP can't share logic across that boundary): the confirmation page (`StepConfirmation.vue`) builds a downloadable `.ics` VEVENT client-side (a `Blob`/`URL.createObjectURL()` download, no server round trip) plus a Google Calendar `render?action=TEMPLATE` deep link; the `{add_to_calendar_link}` email placeholder (`BYZO_Notifications::google_calendar_link()`) is the Google Calendar link only — a downloadable file has no natural place in a plain-text email without new streaming infrastructure this feature doesn't call for, so the email placeholder is deliberately narrower than the confirmation page. No new column or token needed either way — this is a single-event link, not the subscribable multi-event feed (that's B9's calendar feed, which does need a token, see §4).

- **SMS + WhatsApp + multi-reminder timing — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 7 (`FEATURES.md` B5).** `FEATURES.md` B5 scopes SMS/WhatsApp to exactly 3 events — confirmation, cancellation, reminder (not `booking_created`/`admin_new_booking`) — and separately wants reminder *timing* itself configurable (e.g. 48h + 2h, not Free's fixed 24h). These turned out to need two genuinely different mechanisms, not one:
  - **Confirmation/cancellation (immediate, unconditional)**: `BYZO_Notifications::send()` gained one new hook, `do_action( 'byzo_notification_channels', $event, $booking, $placeholders )`, fired right after `wp_mail()` using the SAME already-built placeholder array — no Free-side duplication. `bookyzo-pro`'s `BYZOP_Reminders` listens for `booking_confirmed`/`booking_cancelled` only (deliberately NOT `booking_reminder` here — see below) and sends SMS/WhatsApp alongside whatever email Free already sends, when the customer has a phone number and the channel is configured.
  - **Reminders (scheduled, per-rule, customizable timing)**: can't reuse the hook above — a rule might want SMS-only with no email at all, which `send()`'s unconditional `wp_mail()` call doesn't support. Free's fixed 24h reminder cron (`BYZO_Notifications::send_reminders()`) is left **completely untouched** — Pro's rules are additive, not a replacement (an admin who configures a rule at 24h too gets a harmless duplicate reminder; not worth complicating the design to prevent, it's the admin's own overlapping config). Pro runs its **own** hourly cron reading `byzop_settings.reminder_rules` (array of `{id, offset_hours, channels}}`, empty by default — same "don't invent live config the admin never asked for" precedent as `business_hours`/deposits), matching bookings by the same hour-window technique `send_reminders()` already uses, against a **new Free-side query method** `BYZO_Booking::get_bookings_in_window()` (added, not a variant of the existing `get_due_for_reminder()` — that method's own `reminder_sent_at IS NULL` filter is specific to Free's single fixed reminder and would wrongly exclude a booking from ALL of Pro's independent rules the moment Free's own 24h reminder had already fired for it once).
  - **New Pro-owned table `wp_byzo_reminder_log`** (`byzop_db_version` 1.0→1.1): `booking_id`, `rule_id`, `channel`, `sent_at`, UNIQUE `(booking_id, rule_id, channel)` — tracks each (booking, rule, channel) triple independently, so a rule with `channels: ['email','sms']` where SMS fails (bad API key) retries just SMS on the next cron pass without re-sending the email that already succeeded. This is the thing Free's single `reminder_sent_at` column structurally cannot represent for more than one rule, which is why it's a new table rather than widening that column.
  - **SMS gateway: Twilio**, hardcoded (not a registry) — same evolutionary choice as Stripe-before-the-payment-registry: build one real gateway first, generalize into a filter/registry only once a second one is actually being added (PayPal's own build just proved why an untested "it'll be a registry" claim is worth less than actually building the second consumer first).
  - **WhatsApp: Meta's WhatsApp Cloud API** (explicitly named in `FEATURES.md`/ROADMAP.md, not a generic "WhatsApp Business API" reseller) — phone_number_id + a permanent access token, REST calls to `graph.facebook.com`.
  - **Templates**: new Pro-owned option `byzop_message_templates`, plain-text-body-only (no subject — SMS/WhatsApp have none), keyed `[channel][event]`, same 3 events as above. Reuses the exact `{placeholder}` tokens `BYZO_Notifications` already builds for email — no separate placeholder vocabulary to keep in sync.
  - **NOT independently verified against a live Twilio/WhatsApp Cloud API account** — no credentials available in this environment, same caveat every third-party API integration in this project has carried until a later session tested it for real (Stripe, then PayPal).

### A7. Payments
- Manual/offline: just a "Mark as paid" button in admin, sets `payment_status = paid_manual`
- One gateway (Stripe) via Stripe Elements on the confirmation step; `byzo_payment_intent` created server-side, webhook `wp-json/bookyzo/v1/stripe-webhook` confirms and flips `payment_status = paid_online` + `status = confirmed`
- **Two paths write that status, not one (fixed 2026-09-11).** The webhook alone left every booking `unpaid` on any site Stripe cannot reach — a local or staging install, a firewalled host, or simply a webhook endpoint the owner hasn't configured yet — even though the card had genuinely been charged. The widget now also calls `POST /bookings/{id}/confirm-payment` as soon as Stripe confirms the card client-side. That endpoint does **not** trust the browser: it takes only an intent id, re-fetches the PaymentIntent from Stripe server-side (`BYZO_Stripe::get_payment_intent()`), and requires both `status = succeeded` and `metadata.booking_id` equal to the booking being confirmed — so a forged or borrowed intent id fails. The two paths are intentionally redundant and idempotent: whichever arrives first flips the status, the second is a no-op (the `pending` guard means the status transition fires once). A failure of the client-side call is swallowed rather than surfaced — the money is already taken, so blocking the confirmation screen would be worse than leaving the webhook (or the owner) to reconcile. Verified end-to-end against real Stripe test-mode keys with card `4242…`, which also closed the "never verified against a live Stripe account" caveat that had stood in `BYZO_Stripe`'s own docblock since Phase 1.
- No deposits on Free — full amount or nothing; bookable item/service price is a flat field on the bookable item (`price` column, see §1.1) for Free's single-service-per-type model
- **Deposits/partial payments (BUILT 2026-09-11, Phase 2 step 6).** New `bookings.deposit_amount` column (`BYZO_DB_VERSION` 1.8→1.9, NULL = pay in full, today's exact Free behavior) — resolved in `BYZO_Booking::attempt_create_on_slot()` via `BYZO_Capabilities::deposits_enabled()` (master on/off, Free=false) gating a `byzo_deposit_amount` filter (the actual amount, percentage-of-total or fixed, clamped to `[0, payment_amount]` so a misconfigured Pro filter can never overcharge). `BYZO_Stripe::create_payment_intent()` charges `deposit_amount ?? payment_amount` — the only backend change the payment flow itself needed. Pro's own `byzop_settings` option (`BYZOP_Settings`, deliberately NOT folded into Free's `byzo_settings` — same separation `/payment-settings` already has from `/settings`) holds `deposit_enabled`/`deposit_type`('percentage'|'fixed')/`deposit_value`, edited on Pro's own new "Deposits" screen. Free-side UI changes are purely data-driven, never Pro-gated: `BookingDetailModal.vue` shows "Deposit due online: $X · Balance due: $Y" whenever `deposit_amount` is set and less than `payment_amount` (null for every non-deposit booking); the widget's `StepPayment.vue` shows the deposit/balance split and charges/displays `deposit_amount` when present, exactly matching what Stripe actually bills. No new payment_status value — `paid_online`/`paid_manual` still just mean "what was due online at booking time succeeded"; collecting the balance later is a manual/in-person step today, no separate "collect balance" flow built (deliberately deferred, same as the widget's service picker in B7).
- **Gateway registry (DONE 2026-09-06, ahead of Phase 2 — see the callout below):** `BYZO_Payment_Gateways::all()` returns the list of registered gateways via the `byzo_payment_gateways` filter, defaulting to just Stripe. `byzo_payment_settings` is keyed per-gateway (`gateways.<id>.*`, e.g. `gateways.stripe.enabled/publishable_key/secret_key/webhook_secret`) rather than flat `stripe_*` keys, so a second gateway is a new sub-array, not a shape change. The admin Payments screen (`PaymentSettings.vue`) renders one self-contained on/off block per entry in `GET /payment-gateways` — a plain toggle per method, not a tab switcher, since §B6 has Pro running several gateways *simultaneously*. Free registers only Stripe; when Pro exists it adds PayPal (and candidates like Paddle/Mollie) the same way `BYZO_Capabilities` filters are overridden — no Free-side code changes, no visible locked/disabled entries for gateways that aren't registered (Guideline-5 rule).
- **PayPal (BUILT 2026-09-11/12, Phase 2 step 6) — a second gateway registered the way the paragraph above always intended, and the first real test of that design.** Two gaps surfaced once actually building it (the registry's `defaults()`/`update()` were still hardcoded to Stripe alone, and `PaymentSettings.vue`'s gateway-settings component map had no extension point) — both fixed in Free: `BYZO_Payment_Settings::defaults()` now sources `gateways` through a new `byzo_payment_gateway_defaults` filter (Stripe's own default stays a hardcoded literal, untouched); `update()` validates/merges any non-Stripe gateway id through a new `byzo_validate_payment_gateway_settings` filter, silently ignoring settings for a gateway id nothing currently registers rather than erroring; `PaymentSettings.vue`'s `gatewayComponents` map merges with a new `extraPaymentGatewayComponents` reactive object (`src/lib/admin-extensions.js`) — the SAME `registerExtension()` call Pro already uses for routes/nav items gained a third recognized key, `paymentGatewayComponents`. `bookyzo-pro`'s `BYZOP_PayPal` (own OAuth2 client-credentials token, cached in a transient; Orders API v2 create+capture, no vendor SDK, same `wp_remote_post()` approach as `BYZO_Stripe`) hooks all three filters, only while licensed (matching every other Pro feature this phase). New Pro-owned REST routes `POST /bookings/{id}/paypal-order` and `POST /bookings/{id}/paypal-capture` mirror Free's own Stripe payment-intent/confirm-payment routes byte-for-byte in shape: guest-allowed, guarded by requiring the caller to already know the booking's `customer_email`, and capture never trusts the client's claim — it re-fetches the captured order from PayPal and checks it was actually created for this exact booking (`reference_id`/`custom_id`, both set to the booking id at order-creation time) before flipping `payment_status`. **No PayPal webhook handler exists** — unlike Stripe's redundant webhook+client-confirm design, the direct server-side capture-and-verify call is the only path that marks a PayPal payment paid today; a future hardening pass could add one the same way Stripe's was added, but wasn't required to ship a working v1. **Deliberately out of scope, flagged not silently dropped**: the customer-facing booking widget has no PayPal button yet — `StepPayment.vue` is still Stripe-only. Reworking it to be gateway-aware (show whichever of Stripe/PayPal are actually enabled) is comparable in size to B7's own deferred "any available staff" widget picker; both wait for concrete need. **NOT independently verified against a live/sandbox PayPal account** — no PayPal developer app credentials available in this environment, written strictly to PayPal's documented REST API. Same caveat `BYZO_Stripe` itself carried from Phase 1 step 8 until a later session (2026-09-11, same day as this Phase 2 work) finally tested it against real Stripe test-mode keys — this needs the same live-credentials pass before a real customer relies on it.
- **Flat site-wide tax rate (DONE 2026-09-05 — Phase 1.5 step 9; speced 2026-09-03):** `tax_rate` field (float, percent, 0-100, validated in `BYZO_Settings::update()`) in `byzo_settings`, default 0. When > 0, `BYZO_Booking::create()`'s existing `payment_amount = price × party_size` computation (§ Phase 1 step 8's security fix) gains a second step: `tax_amount = round( subtotal × tax_rate / 100, 2 )`, `payment_amount = subtotal + tax_amount` — both stored per §1.4 (`tax_amount` is `NULL`, not `0.00`, when there's nothing to charge or `tax_rate` is 0). Editable under **Bookyzo → Settings** (`GeneralSettings.vue`). Per-bookable item override (`bookable_items.tax_rate_override`) is Pro-only and **not yet in the schema** — see §1.1's note; Free's settings UI only ever writes the one site-wide rate.

### A8. Dashboard (renamed from "Basic reporting" 2026-09-03 — see `FEATURES.md` A8)
- Simple aggregate query page: `SELECT status, COUNT(*) FROM wp_byzo_bookings WHERE start_datetime BETWEEN ...` grouped by day/week/month
- CSV export via the same `admin-post.php` + nonce pattern used in CBFW's import/export and license-envato's log export
- **`BYZO_Reports::get_dashboard_summary()` gains a `revenue` field (DONE 2026-09-05 — Phase 1.5 step 10; speced 2026-09-03):** new `BYZO_Booking::get_revenue()`, `SUM(payment_amount) WHERE payment_status IN ('paid_manual','paid_online')`, same three periods (today/this-week/this-month) as the existing status counts, same INNER JOIN-onto-slots convention so a booking whose slot was deleted doesn't inflate the total. One number per period, surfaced as a 4th `ByzoStatCard` ("Revenue (this month)") — no bookable item/type/date-range breakdown, that stays Pro (B8).
- **Upcoming bookings widget (DONE 2026-09-05):** `Dashboard.vue` gains a bounded query against the existing `GET /bookings` (`from=now`, `status=pending,confirmed`, `per_page=5`) — no new endpoint, just a narrower call to what A4's list already serves. **`BYZO_Booking::query()` widened to make this possible**: `status` now also accepts a comma-separated list (`IN()` instead of `=`, backward-compatible with every existing single-value caller), and `from` accepts the literal `now` to filter from the current moment rather than midnight — the slot generator never materializes a slot earlier than "now" for today, so without this a single-status/date-only query already happened to look right by accident; the literal `now` support is what makes the distinction real and testable (verified against a directly-entered past-today occurrence, since a generator-created slot can't ever be in the past to test against).
- **Welcome header (DONE 2026-09-05):** one line above the Hero card ("Set up: N active bookable items — Appointment, Table") — a small honest simplification from the original wording here ("reads the... set already fetched for the Bookable Items screen"): Dashboard.vue is a separate route with its own lifecycle, there's no cross-route data cache to reuse in this app, so it makes its own bounded `GET /bookable-items?status=active` call rather than one that was somehow already in memory. Same call also backs the upcoming-bookings widget's item-name lookup, so it's one fetch serving two things, not a wasted one.

### A9. Type-specific Free constraints

With all four types in Free (2026-09-02), this per-type cap is Free's ONLY volume limit: up to 4 active bookable items total, one per type. **Do not scatter "if free, limit to 1" checks across multiple files** — this is exactly the kind of restriction WordPress.org's Guideline 5 reviewer flags if any UI text mentions "free version" while the code path still exists; keep the enforcement as a genuine capability query, not a visible lock (see CBFW's 2026-07-31 and 2026-08-03 Trialware rejection history — do not repeat that mistake here).

## 3. Pro Plugin — Feature-by-Feature Breakdown

### Shared Vue admin app — the actual mechanism (decided/built 2026-09-11, Phase 2 step 1)

Free and Pro are two independently installed/activated/updated WordPress plugins, so "one shared Vue 3 admin app" (the standing rule in bookyzo-dev/bookyzo-design SKILL.md and this doc's own earlier notes) can't mean one literal build spanning both plugin folders — Free's WordPress.org zip is built and shipped long before any given customer installs Pro. The resolved mechanism, entirely **runtime**, not build-time:

- **Pro ships its own separate small Vite bundle** (`bookyzo-pro/src/`, `bookyzo-pro/vite.config.js` → `bookyzo-pro/assets/admin/`), enqueued by `BYZOP_Admin_Assets` on every Bookyzo admin screen, always AFTER Free's own `byzo-admin` script (declared as a hard script dependency). It does **not** mount a second Vue app.
- Free's `src/main.js`, right before mounting, exposes an extension point: `window.byzoAdmin.registerExtension({ routes, navItems, paymentGatewayComponents })` (backed by `src/lib/admin-extensions.js` — `routes` are pushed onto the already-created `router` via `router.addRoute()`, safe to call post-mount; `navItems` are pushed onto a `reactive([])` that `ByzoSidebar.vue` renders after its own built-in items; `paymentGatewayComponents` — added 2026-09-11/12 for PayPal — merges into a `reactive({})` that `PaymentSettings.vue` reads alongside its own hardcoded Stripe entry, so a Pro-registered gateway (`byzo_payment_gateways`, PHP-side) gets a real settings form instead of the "aren't available in this version" fallback).
- **Vue/Vue Router must be the exact same runtime instance**, not two independently-bundled copies — a Vue SFC's composition-API internals (`onMounted`, `inject`, `computed`'s dependency tracking) read module-level state in whichever `vue` copy compiled them; a second bundled copy of `vue` never sees that state set, and hooks silently no-op. So Free's `main.js` also does `window.Vue = Vue; window.VueRouterLib = VueRouterLib;` (namespace imports), and Pro's `vite.config.js` builds in **`build.lib` + `iife` format** with `vue`/`vue-router` marked `external` and mapped via `rollupOptions.output.globals` to those two window globals — this is why Pro's bundle can't just be a normal ES module Vite build (Rollup's `output.globals` only applies to umd/iife, and ES module output has no browser-native way to redirect a bare `import 'vue'` specifier to an existing global without an import map).
- **Script tag ordering gotcha, caught via an actual rendered-page check, not by reasoning alone**: WP dependency ordering only controls *DOM order*, not *execution* order once module and classic scripts are mixed. Free's script is `type="module"` (implicitly deferred — executes after parsing, regardless of DOM position). Pro's script is a classic (non-module, iife) script — **without an explicit `defer` attribute, a classic script executes synchronously the instant the parser reaches its tag**, which can easily be *before* a preceding deferred module script has actually run. `BYZOP_Admin_Assets` adds `defer` via the `wp_script_attributes` filter for exactly this reason — with it, Pro's script joins the same "execute after parsing, in document order" queue the HTML spec puts non-async module scripts in, so the two run in the correct relative order. Verified with a real headless-Chrome fetch of the rendered admin page (`window.Vue`/`window.byzoAdmin.registerExtension` present, License nav item renders, zero console errors) — this bug would NOT have been caught by build success or a PHP smoke test alone.
- Pro's own Vue components use **plain hand-written CSS** against Free's already-loaded `--byzo-*` custom properties, not Tailwind/shadcn-vue — pulling in a second full Tailwind+shadcn-vue build for a cross-plugin-boundary bundle isn't worth it yet (same "plain CSS, not Tailwind" precedent as the public widget bundle). Revisit if/when a Pro screen actually needs the fuller component vocabulary.
- Pro's own `src/api/client.js` is a byte-for-byte duplicate of Free's (can't literally import across the plugin boundary) — thin `wp.apiFetch` wrapper scoped to the `bookyzo/v1` namespace, relying on Free's inline nonce-middleware setup already having run (guaranteed by the same script-dependency chain above).

### B7 (Appointment). Services & "any available staff" auto-assignment — DESIGNED + BUILT 2026-09-11, ROADMAP.md Phase 2 step 5

`FEATURES.md` B7's Appointment section lists this as two bullets ("staff-specific service assignment and pricing", "'any available staff' auto-assignment") with no technical detail anywhere — this section is the design written before coding (per the user's explicit request — steps 1-4 didn't need this; this one did, being a real new sub-system rather than a single filter override), now built and verified against it.

**Backend fully built and tested (41 checks, `bookyzo-pro/scratchpad/smoke-phase2-step5-services.php`, plus a live REST-dispatch regression against the existing direct-booking path).** **Admin UI built**: Pro's own "Services" screen (`bookyzo-pro/src/views/ServicesList.vue`, reached via the shared-Vue-extension mechanism — DETAILED-SPEC.md §3 — same as the License screen) — create/edit a service and manage which staff offer it + their price overrides all in one place, verified end-to-end in a real headless-Chrome run (create → assign 2 staff with one override → save → reload → edit → override round-trips correctly, zero console errors). **Deliberately deferred, not silently dropped**: the customer-facing public widget UI for "browse by service, get any available staff" — the backend fully supports it (`GET /slots?service_id=`, `POST /bookings` with `service_id`+`start_datetime`) and is proven working by the smoke test's own booking-assignment checks, but the widget's own step components (`src/widget/`) haven't been touched; today a service-based booking is only reachable via direct API/REST calls, not through the actual booking widget a site visitor uses. Build the widget picker when there's a concrete reason to (same "don't build UI ahead of the feature that reads it" precedent already applied elsewhere in this project).

**Core tension found while designing, and how it's resolved**: Free's whole booking model assumes one bookable item (= one staff member) offers exactly one fixed-duration service, and slots are *materialized* per bookable item at that one duration (§1.3's "why" note — atomic `capacity_remaining` decrements need a real row to decrement). If "staff-specific service" also meant a per-(staff, service) duration, the same staff's calendar would need a DIFFERENT slot stream per service they offer (a 30-min haircut and a 90-min coloring can't share one materialized-slot timeline without a real rework of §1.3's core model) — a much bigger, riskier change than this step implies. `FEATURES.md`'s own wording only promises "**pricing**," not duration, which resolves this cleanly: **duration stays exactly what it is today — the bookable item's own `duration_minutes`, unchanged, still drives that staff member's one slot stream.** "Service" is a shared name + price label layered on top, not a new scheduling unit. This keeps §1.3's materialized-slot architecture, its atomic capacity decrement, and `BYZO_Slot_Generator` completely untouched.

**New Pro-owned tables** (created in `bookyzo-pro`'s own activation hook, first real Pro tables actually built — `wp_byzo_locations`/`wp_byzo_pricing_rules`/etc. were reserved in this doc since 2026-09-02/03 but none exist as real code yet either):
- `wp_byzo_services`: id, name, description NULL, default_price DECIMAL(10,2) NULL, status ('active'/'inactive'), created_at, updated_at.
- `wp_byzo_bookable_item_services` (join table): id, bookable_item_id (FK), service_id (FK), price_override DECIMAL(10,2) NULL (NULL = use the service's `default_price`), UNIQUE (bookable_item_id, service_id).

**New Free-schema column** (don't gate the data model, same principle as `addons`/`custom_fields`/`attendees`): `wp_byzo_bookings.service_id BIGINT UNSIGNED NULL` — which service was booked; NULL for every booking made the way Free already works (direct staff pick, no service concept). Needs a `BYZO_DB_VERSION` bump when built (currently 1.7).

**Booking flow ("any available staff")**: the customer picks a service (not a specific staff member) in the widget. `GET /slots` (existing, Free-owned, §4) widens to accept `service_id` as an alternative to `bookable_item_id` — resolves to every bookable item in `wp_byzo_bookable_item_services` for that service, returns the UNION of their open slots by `start_datetime` (client sees one list of bookable times, not a per-staff breakdown). `POST /bookings` widens the same way: given `service_id` + a chosen `start_datetime` instead of a specific `slot_id`, the server tries each qualifying bookable item's slot row at that datetime in turn, atomically claiming the first one whose `capacity_remaining` decrement succeeds (same per-row atomic UPDATE §Phase-0-step-6 already uses, just attempted across N candidate rows instead of one) — genuinely "any available staff," decided server-side, never trusted from the client. A customer who explicitly wants a specific staff member can still pass `bookable_item_id` directly, unchanged from today.

**Price resolution**: when a booking carries a `service_id`, `payment_amount` computes from the resolved service price (`wp_byzo_bookable_item_services.price_override` for the assigned staff member, falling back to `wp_byzo_services.default_price`) instead of the bookable item's own `price` column. A booking with no `service_id` (every Free booking, and any Pro booking made by picking a staff member directly without going through a service) is completely unaffected — same `price × party_size` computation as today.

**New REST endpoints (Pro-registered, via `byzo_rest_controllers`, same pattern as `/license`)**: `GET/POST /services`, `GET/PUT/DELETE /services/{id}` (admin CRUD); `GET /services/public` (active only, for the widget); `GET/PUT /bookable-items/{id}/services` (assign/unassign + per-staff price overrides for one bookable item). `/slots` and `/bookings` widen in Free's own controllers (a REST surface widening, not a schema change — same category of change as B3's timeline-view widening above), gated so the `service_id` param path is simply unreachable/inert without Pro's tables existing to resolve against.

**Scope deliberately left out of this step** (flag if the user wants them folded in): staff calendar sync (already its own ROADMAP step 9) and commission/payout tracking (not assigned to any step yet — smallest, most analytics-shaped of the three B7-Appointment bullets, probably belongs near Phase 2 step 10's analytics work instead).

### B7 (Appointment). Staff calendar sync — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 9

Genuinely different shape from every prior Pro integration: Stripe/PayPal/Twilio/WhatsApp are all static-key server-to-server calls. Google Calendar and Outlook both require an interactive OAuth2 authorization-code flow (consent screen, redirect URI, refresh token) per connected calendar. Decided directly (enough architectural precedent from steps 1-7 to not need to stop and ask) rather than raised to the user, because the one genuinely open question — who owns the OAuth app credentials — only has one realistic answer for a self-hosted plugin with no vendor-side relay: **bring-your-own**. The site admin creates their own Google Cloud OAuth client and Azure AD app registration (same pattern every self-hosted WP calendar-sync plugin uses) and pastes Client ID + Client Secret into Pro's own settings; Codeholt's license server is untouched, no new server-side infrastructure needed. Same "written to spec, not live-tested" caveat every third-party integration in this project has carried (Stripe, then PayPal, then Twilio/WhatsApp) — no live Google/Microsoft app available in this environment.

**Free-side change — the entire thing is two new methods, no schema/no DB version bump.** `wp_byzo_slots.status` already has a live `'blocked'` value (`BYZO_Slot_Generator::block_slots_on_dates()`, built Phase 0 for blackout dates) that every open-slot query (`BYZO_Slot::query()`/`open_at()`) and the atomic booking-claim UPDATE (`BYZO_Booking::attempt_create_on_slot()`) already treat as unbookable — the exact "let the real wall answer honestly" mechanism this project keeps reusing. Calendar sync's pull direction is just a second writer of a status value that already fully works: `BYZO_Slot::block( $slot_id )` / `unblock( $slot_id )`, single-row status flips (`open`→`blocked` / `blocked`→`open`, each guarded by the current status so it can never stomp a row a blackout or a booking claim already touched). Push direction needs zero new hooks — `byzo_booking_created`, `byzo_booking_status_changed`, and `byzo_booking_rescheduled` (all three already fire with everything needed) are enough.

**New Pro-owned tables** (`bookyzo-pro`'s own activation hook, `BYZOP_DB_VERSION` 1.1→1.2):
- `wp_byzo_calendar_connections`: id, bookable_item_id (FK), provider (`'google'`/`'outlook'`), access_token, refresh_token, token_expires_at, external_calendar_id (which calendar to write to, default `'primary'`), sync_enabled, last_synced_at, created_at, updated_at. UNIQUE (bookable_item_id, provider) — a bookable item can connect Google AND Outlook at once, not either/or.
- `wp_byzo_calendar_event_map`: id, connection_id (FK), booking_id (FK), external_event_id, created_at. UNIQUE (connection_id, booking_id) — push-sync's own bookkeeping, lets an update/cancel find the right external event to patch/delete.
- `wp_byzo_calendar_blocked_slots`: id, connection_id (FK), slot_id (FK), external_event_uid, created_at. UNIQUE (connection_id, slot_id) — pull-sync's own bookkeeping; each hourly reconcile pass only ever unblocks a slot row it itself blocked, tracked by id, never a blind date-range unblock that could reopen a real blackout.

**OAuth + provider calls**: `BYZOP_Google_Calendar` (`accounts.google.com/o/oauth2/v2/auth` with `access_type=offline&prompt=consent` to force a refresh token, `oauth2.googleapis.com/token`, Calendar API v3 `events`/`freebusy`) and `BYZOP_Outlook_Calendar` (Microsoft identity platform v2 `/authorize`+`/token`, scope `Calendars.ReadWrite offline_access`, Graph API `/me/events`+`/me/calendarView`) — same duck-typed-pair shape as step 7's `BYZOP_SMS`/`BYZOP_WhatsApp` (two known providers, hardcoded, no registry — a registry is only worth building once a third consumer actually shows up, per the PayPal lesson). `BYZOP_Calendar_Sync` orchestrates both: hooks the three Free actions above (fire-and-forget via `wp_schedule_single_event`, same non-blocking shape planned for step 15's webhooks, so a slow Google/Microsoft API call never holds up the booking request) for push, and a new hourly cron `byzop_sync_calendars` (registered alongside step 7's `byzop_send_reminders` in `BYZOP_Activator::maybe_schedule_cron()`) for pull.

**OAuth state/CSRF**: the `state` param carries a signed nonce (`wp_salt('auth')`-keyed HMAC over bookable_item_id + provider + admin user id + expiry) — same signed-token shape as `BYZO_Booking_Token`/`BYZO_Calendar_Feed_Token`, the only way to authenticate a mid-redirect callback that can't carry normal REST auth.

**New Pro REST routes** (`bookyzo/v1`, same shared namespace every Pro REST controller registers into via `byzo_rest_controllers`, admin-only except the callback): `GET /calendar-sync/{bookable_item_id}` (connection status, never returns raw tokens), `POST /calendar-sync/{bookable_item_id}/connect` (body `{provider}`, returns `{authorize_url}`), `GET /calendar-sync/{provider}/callback` (public, gated entirely by the signed `state`, exchanges code → tokens → redirects back into wp-admin), `DELETE /calendar-sync/connections/{connection_id}` (disconnect).

**Admin UI**: new "Calendar Sync" screen — per-bookable-item connect/disconnect buttons, last-synced time, and a settings section for pasting each provider's Client ID/Secret plus the site's own fixed callback URL (`rest_url('bookyzo/v1/calendar-sync/{provider}/callback')` — note the route lives in Free's shared `bookyzo/v1` namespace like every other Pro REST controller, not a separate `bookyzo-pro/v1`) to copy into the Google/Microsoft app config. If a provider's credentials aren't configured yet, the connect button is simply absent with a plain instructional line — no lock icon, no upsell copy (Guideline 5).

**A pre-existing bug found and fixed while building this**: Free's Vue Router resolves its very first navigation's match *synchronously*, during `main.js`'s own execution — before Pro's deferred script has run and called `addRoute()`. Purely SPA-internal navigation (clicking a sidebar link) was never affected, since by then Pro's script has long since run; but a genuine fresh page load landing directly on a Pro route (a bookmark, a reload, or — the case that actually surfaced it — this step's own OAuth callback redirecting the browser back to `/pro/calendar-sync`) hit an empty route match and rendered a blank content area. This silently affected every Pro admin screen since Phase 2 step 1, just never had a code path that needed a genuine server-initiated full-page redirect before now. Fixed in Free's `src/router/index.js`: `router.isReady().then(() => { if (no match) router.replace(current path); })` — a one-time self-heal once the initial navigation (and every deferred script on the page) has definitely settled.

### B8. Analytics dashboard — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 10

`FEATURES.md` B8 lists 7 items; **conversion rate is explicitly out of scope here** — it's blocked on §5 Open Decision 11's unresolved view-tracking mechanism and belongs to its own later step (step 19), not this one. Everything else (revenue breakdown, occupancy rate, no-show tracking, repeat-customer metrics, popular bookable items/hours, trend charts) is in scope. Designed directly (enough precedent by step 10 not to need a stop-and-ask) by extending Free's own existing report-query conventions — `BYZO_Reports`/`BYZO_Booking::get_status_counts()`/`get_revenue()`/`get_daily_counts()`, all already `DateTime $from, DateTime $to` range-scoped, INNER JOIN onto `wp_byzo_slots` for appointment-time filtering rather than `created_at`.

**Step 19 (analytics depth) confirmed subsumed by this step, closed 2026-09-12 with no new code**: `get_popular_bookable_items()`/`get_popular_hours()`/the trend chart already cover step 19's entire "popular bookable items/time slots/staff, booking trend charts" scope — Appointment-type bookable items ARE staff in this project's model, so there was never a distinct "popular staff" query left to build. Conversion rate remains the one genuinely unbuilt B8 item, still blocked on §5 item 11.

**Same architectural principle as steps 5/7/9's Free-side additions**: any new query against a Free-owned table's own data goes into Free's own data-access class (`BYZO_Booking`/`BYZO_Slot`/`BYZO_Customer`), never as raw SQL written inside Pro against Free's tables directly — keeps one authoritative query surface per table regardless of which plugin actually calls it. No schema change, no `BYZO_DB_VERSION` bump — every metric here is a read-only aggregate over columns that already exist.

**New Free methods** (`BYZO_Booking`, same file/class the existing report methods already live in):
- `get_revenue_by_bookable_item( $from, $to )` / `get_revenue_by_type( $from, $to )` — same `SUM(payment_amount) WHERE payment_status IN (...)` as the existing `get_revenue()`, grouped.
- `get_no_show_rate( $from, $to )` — `no_show / (completed + no_show)`, overall and per bookable item. Deliberately excludes `cancelled`/`rejected`/`pending` from the denominator — a no-show rate is about people who booked and didn't show, not about every booking outcome.
- `get_popular_bookable_items( $from, $to, $limit = 10 )` / `get_popular_hours( $from, $to )` — booking counts grouped by `bookable_item_id` / `HOUR(s.start_datetime)`.

**New Free method** (`BYZO_Slot`): `get_occupancy_by_bookable_item( $from, $to )` — **occupancy rate is defined as the fraction of a bookable item's offered time slots that received at least one booking**, not a capacity-weighted fill rate. `wp_byzo_slots.capacity_remaining` is mutated in place with no stored "original capacity" column, so there's no reliable way to compute a true capacity-weighted number for a slot generated under a since-changed capacity setting — rather than build a guess on top of missing data, occupancy here answers "how much of this bookable item's offered time actually got used," matching how occupancy is commonly reported for rooms/tables (occupied vs. total), not covers-served. `LEFT JOIN` slots (`status IN ('open','full')`, excluding `'blocked'` — a blackout/calendar-sync-blocked slot was never actually offered, so it doesn't belong in the denominator) onto non-cancelled/rejected bookings, `COUNT(DISTINCT slot id with a match) / COUNT(DISTINCT slot id)`.

**New Free method** (`BYZO_Customer`): `get_repeat_customer_stats()` — **deliberately NOT date-range-scoped like every other metric here** — retention is inherently a whole-history question ("has this customer been back at all"), not a "in the last 30 days" one; scoping it to the dashboard's selected range would make the number bounce around based on window choice rather than reflect actual repeat behavior. Returns `{ total_customers, repeat_customers (>=2 non-cancelled/rejected bookings, all time), repeat_rate }`.

**Trend chart**: reuses `BYZO_Reports::get_dashboard_trend()`/`BYZO_Booking::get_daily_counts()` unchanged — already public, already range-flexible (7-90 days) — Pro's screen just calls it with its own selected range instead of Free's fixed Dashboard number.

**New Pro REST route**: `GET /analytics?from=&to=` (admin-only, only registered while licensed, same gating shape as every other Pro controller) — one bundled response (`{ revenue_by_bookable_item, revenue_by_type, occupancy, no_show, popular_bookable_items, popular_hours, trend, repeat_customers }`), matching `BYZO_Reports::get_dashboard_summary()`'s own "one call, several sections" shape rather than forcing the admin screen into N round trips.

**CSV export**: `BYZOP_Analytics_Export` mirrors Free's own `BYZO_Booking_Export` (`admin-post.php` + nonce, not REST — a file download doesn't fit a JSON response) — one CSV with a section per breakdown (revenue by bookable item, revenue by type, occupancy, popular items, popular hours), for the same date range the screen is showing. **Scheduled email reports (the other half of B8's "Exportable reports" bullet) are explicitly NOT built** — flagged rather than silently dropped, since it needs its own cron + email template design and isn't required to ship the dashboard itself; a natural candidate for a later step if there's demand.

**Admin UI**: new "Analytics" screen — a date-range picker (defaulting to this month, reusing the same period options the rest of the admin app already uses) plus stat cards + simple bar/list breakdowns for each section (no charting library — same plain-hand-written-CSS approach as every other Pro screen; a trend line is rendered as simple CSS bars, matching how Free's own Dashboard trend chart already works without a chart library).

### B3. Advanced Booking Management — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 11

Three bullets, three different Free/Pro shapes once actually examined against the current architecture — decided directly, enough precedent by step 11 not to need a stop-and-ask.

**Drag-and-drop reschedule on the calendar — RECLASSIFIED FREE, not Pro.** `FEATURES.md`'s B3 bullet predates a fact that's been true since Phase 1.6: `PUT /bookings/{id}/reschedule` (`BYZO_Booking::reschedule()`) has never had a capability check — it's a completely unrestricted Free action already, reachable today via the booking detail modal's own slot-picker dropdown (A4's "Basic reschedule," `FEATURES.md` line 63, which explicitly calls the calendar drag version "the visual/bulk version of the *same underlying action*"). Gating the drag gesture specifically — while the dropdown-triggered call to the exact same endpoint stays free — would mean inventing a distinction with no real backend difference behind it (which UI element the click started from), the same shape of mistake `bookyzo-dev/SKILL.md` already documents from the sister plugin's Guideline 5 rejections. Since it's the same already-free capability, it ships in Free: `ByzoCalendarWeek.vue` gained native HTML5 drag-and-drop (`draggable` on each booking block, drop targets on the hour-cell grid) — dropping on a new day/time resolves the target slot via the already-public `GET /slots` (matched by nearest real generated slot's `start_datetime`, not an arbitrary continuous drop position — a slot has to actually exist there) and calls the SAME unrestricted reschedule endpoint the modal's dropdown already uses. No new REST route. Dropping on a time with no real open slot fails honestly (a `vue-sonner` toast, same as every other error in this app) rather than silently snapping to the nearest anything — matches the "let the real wall answer honestly" pattern this project keeps reusing (§3 B7's own note on `wp_byzo_slots.status`).

**Bulk actions (bulk cancel, bulk status change) — genuinely Pro**, unlike the above: there's no existing Free multi-select/bulk UI or endpoint to re-skin, so this is real new capability, not a re-gate of something already free. New Pro-only REST route `POST /bookings/bulk-status` (body `{ids, status}`, admin-only, licensed-gated) loops Free's own `BYZO_Booking::update_status()` per id — reusing its existing `TRANSITIONS` state-machine guard unchanged, so a row that can't legally reach the target status fails on its own without blocking the rest of the batch — and returns `{succeeded: [...ids], failed: [{id, error}...]}`, a partial-success shape rather than all-or-nothing, matching how booking status transitions are already inherently per-row business rules.

**Booking notes/internal tags (staff-only visibility) — genuinely Pro data.** New Free-schema columns on `wp_byzo_bookings` (`BYZO_DB_VERSION` 1.9→2.0, same "don't gate the data model" pattern as every other Pro-consumed Free column): `internal_notes TEXT NULL` (deliberately separate from the existing customer-submitted `customer_notes` — different author, different audience, conflating them would leak a customer's own note into what's supposed to be staff-only) and `tags VARCHAR(255) NULL` (comma-separated, matching `wp_byzo_customers.tags`'s existing shape for consistency). `BYZO_Booking::update_notes_tags( $id, $notes, $tags )` is the one new Free method (a plain field UPDATE, no status-transition logic involved) — the REST route that actually calls it (`PUT /bookings/{id}/notes`) lives entirely in Pro, admin-only, licensed-gated. Free's own `BookingDetailModal.vue` is left completely unchanged — it never writes these columns, so a Free booking's `internal_notes`/`tags` are always empty; showing an always-blank section there would be clutter, not a "lock," so it simply isn't shown at all (nothing to see is not the same as something disabled).

**Admin UI**: since Pro can't inject a checkbox/select column or an inline notes editor into Free's already-compiled `BookingsList.vue` (the same cross-bundle limitation §3's "Shared Vue admin app" note and step 3's shift-adding decision already ran into), bulk actions + notes/tags get their own new Pro screen ("Bulk & Notes," deliberately named distinctly from Free's own "Bookings" nav item so it reads as a companion tool, not a competing/duplicate list) — reuses Free's existing `GET /bookings` (already filterable by date/status/bookable item) for the table, adds checkboxes + a bulk-action toolbar (Confirm/Complete/Cancel/No-show) that appears once 1+ rows are selected, and a per-row expandable notes/tags editor. Capped to the same `per_page=100` Free's own list already enforces — no new pagination UI, matching the "fine at the scale this realistically needs" scope-stopping precedent used elsewhere (e.g. step 5's deferred widget service-picker).

### B7 (Slot/Class). Recurring class series — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 12

Step 12 lists three type-specific modules (Table, Event, Slot/Class) with no user-specified priority and no real-install usage data to sequence by yet (its own ROADMAP.md text says "sequence by which type's Free users show up asking," which doesn't resolve anything pre-launch). Picked **Slot/Class** to go first: its three `FEATURES.md` bullets are the smallest, most self-contained of the three modules — Table's "visual floor plan editor" and Event's "QR e-tickets + web check-in scanner" are both substantially larger, genuinely new UI paradigms (a spatial/canvas editor; camera-based scanning) that deserve their own sizing/design pass rather than being bolted on alongside a first type module. Flagged to the user, not decided silently.

**Scope: this step builds "recurring class series" only** (the first of Slot/Class Pro's three bullets) — "class package redemption" and "instructor/bookable item rotation" are explicitly deferred, not silently dropped, each being a meaningfully separate chunk of work (package redemption is a new payment MODE, not just a UI addition; rotation only matters once series enrollment itself exists). A future step can pick either up once there's a concrete reason to.

**The key architectural simplification, found by tracing through what a "series" actually needs**: a recurring class series does NOT need its own recurrence engine. `BYZO_Slot_Generator` already materializes real slot rows every week from a bookable item's existing weekly schedule (§1.3) — a "series" is just a *reference* to N of those already-generated slots that share the same weekday+time across N consecutive weeks, enrolled by the same customer. So a series enrollment is nothing more than N individual bookings, each created through the exact same atomic-capacity-claim `BYZO_Booking::create()` every other booking already goes through (no new capacity/concurrency logic needed), grouped under one Pro-owned series record afterward. **Zero Free-side changes this step** — every Free method this calls (`BYZO_Slot::query()`, `BYZO_Booking::create()`/`update_status()`) already existed unchanged.

**New Pro tables** (`byzop_db_version` bump): `wp_byzo_class_series` (id, bookable_item_id, customer_name/email/phone, weekday, start_time, occurrences_total, status ['active'/'cancelled'], created_at) and `wp_byzo_class_series_bookings` (id, series_id, booking_id, occurrence_date — the join that lets the admin see/cancel one occurrence vs. the whole series without re-deriving it from bookings each time).

**Enrollment (`BYZOP_Class_Series::enroll()`)**: given a bookable item, weekday+time, customer details, and a requested occurrence count, resolves the next N chronological slots matching that weekday+time via `BYZO_Slot::query()` (already public), then calls `BYZO_Booking::create()` once per matched slot. **A real slot-generator constraint surfaced and handled honestly, not glossed over**: the generator only materializes a rolling window (`byzo_settings.max_advance_days`, business-configured), so a series requesting more occurrences than currently exist within that window can't be force-extended without overriding a setting the business owner deliberately chose — enrollment claims however many real slots currently exist and reports the shortfall (`{enrolled: N, requested: M}`) rather than silently enrolling fewer than asked or fabricating slots that don't exist yet. **Admin-only for this step**, same "customer self-service comes later, once there's concrete need" deferral pattern as step 5's widget service-picker and step 6's PayPal widget button — enrollment happens from Pro's own admin screen (staff enrolling a customer who signed up in person/by phone), not the public booking widget.

**Cancellation**: cancelling the whole series loops the existing `BYZO_Booking::update_status()` (cancel) over every linked booking — same transition guard, same capacity-release logic, already correct with zero new code; cancelling a single occurrence is the same call against just that one booking. Both reuse Free's booking cancellation exactly as the admin calendar's own detail modal already does.

**New Pro REST routes** (`bookyzo/v1`, admin-only, licensed-gated): `POST /class-series` (enroll), `GET /class-series` (list, with each series' linked occurrences), `DELETE /class-series/{id}` (cancel the whole series), `DELETE /class-series/{id}/occurrences/{booking_id}` (cancel one occurrence).

**Admin UI**: new "Class Series" screen — an enrollment form (bookable item, weekday+time picker sourced from that item's real generated slots so an admin can't request a combination that doesn't exist, customer details, occurrence count) and a list of active series, each expandable to its individual occurrences with a per-occurrence cancel action alongside a whole-series cancel.

### B11. Custom form field builder — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 16

**Genuinely novel, worth a real design pass**: every prior Pro feature this phase either lived entirely inside the shared Vue **admin** app (which Pro can extend via `window.byzoAdmin.registerExtension()`, §3's "Shared Vue admin app" mechanism) or was pure backend (webhooks, calendar feed, pricing). This is the **first** feature that needs the customer-facing **public widget** (`src/widget/`, a completely separate Vite bundle with no extension mechanism of its own — Pro has never touched it before) to actually render something Pro-defined. Two shapes were considered: (a) build a parallel Pro-owned widget-extension mechanism (a second `registerExtension`-style API for the widget bundle), or (b) keep the widget bundle 100% Free-owned and dumb, with Pro only ever supplying *data* through a filter Free already calls. **(b) was chosen** — it needs no new cross-bundle infrastructure at all: the widget already fetches its own data over REST (bookable items, slots); a "what custom fields apply to this bookable item" fetch is just one more of those calls, and the actual field *definitions* come from a **new Free-side filter**, not from Pro-authored Vue code running inside Free's bundle. This keeps the public widget genuinely Free-ownable end to end (same guarantee "deactivating Pro degrades gracefully" already promises for the admin app) and avoids the real complexity/security surface of loading a second plugin's JS into a guest-facing, no-nonce, cache-friendly bundle.

**The write side already existed and needed zero changes**: `bookings.custom_fields` (LONGTEXT/JSON) has been reserved on Free's own schema since Phase 1.7, and `BYZO_Booking::validate_for_create()`/`create()` already accept-and-store an arbitrary `custom_fields` object verbatim (no validation against field *definitions* — same "Free stores the shape, Pro defines the meaning" split already used for `addons`/`attendees`). Only the **read** side (what fields exist, so the widget knows what to render) and the widget UI itself were missing.

**New Free filter**: `byzo_custom_fields_for_bookable_item( array $fields, int $bookable_item_id )` — default `array()`. Pro hooks this to return its own active `wp_byzo_custom_fields` rows (global `bookable_item_id IS NULL` rows plus ones scoped to this specific item, sorted by `sort_order`), each shaped `{id, label, field_type, options, required}`. **New Free REST route**: `GET /custom-fields/public?bookable_item_id=` (public, `public_permissions_check()`, matches the already-established `/bookable-items/public`/`/services/public` "same resource, separate `/public` suffix rather than splitting HTTP methods for one path across two controllers" convention — corrects this project's own much-earlier speculative REST-table row, which had guessed at a single split-methods `/custom-fields` path before that convention existed in practice) — just calls the filter and returns the result, so an unlicensed/no-Pro site returns `[]` and the widget step below renders nothing, not a blank/broken section.

**Widget UI**: `StepDetails.vue` (the existing contact-form step — name/email/phone/notes) fetches `/custom-fields/public?bookable_item_id=` once the item is known and renders a small generic field-type-to-input map (`text`, `dropdown`, `checkbox`, `date`, `number`, `address`) after the fixed fields, collecting values into `form.custom_fields = { [field.id]: value }`; `required` fields participate in the same `canSubmit` computed the fixed fields already use. `BookingWidget.vue`'s `onDetailsSubmit()` passes `custom_fields: form.custom_fields` straight through to `createBooking()` — the one line that needed changing in the existing submit path.

**Deliberately deferred, flagged not silently dropped**: the **`file` field type** (needs an actual upload endpoint, storage location, and security scanning — a materially bigger, separate feature, the same class of "looks like a UI addition, is actually a new subsystem" call already made for class-package-redemption and cart-checkout-UI) and **Google-Maps-autocomplete-linked address fields** (the `address` type ships as a plain text input for v1; the `options` column's "Google-Maps-linked config" possibility from the original schema note is left for whenever a concrete need shows up, same "don't build for hypothetical future requirements" principle applied everywhere else in this project).

**New Pro table** `wp_byzo_custom_fields` (§1.6) — the originally-speced columns (`id`, `bookable_item_id NULL`, `label`, `field_type`, `options` JSON NULL, `required`, `sort_order`) plus one addition not in the original plan: a `status VARCHAR(20)` column (`active`/`inactive`), for parity with every other Pro CRUD table this phase (pricing_rules, webhooks, services) — lets an admin temporarily disable a field without losing its configuration or deleting real submitted data's meaning. **New Pro REST routes**: `GET/POST /custom-fields` (admin-only list-all/create) and `PUT/DELETE /custom-fields/{id}` (admin-only update/delete) — plain CRUD on the Pro-owned table, hooking the Free filter above to expose only `status = 'active'` rows to the public route. **Admin UI**: new "Form Fields" screen (per-bookable-item or global scope picker, field list with type/required/status, add/edit modal with type-specific config — options list for `dropdown`).

### B6. Add-ons/extra services + flat booking fee — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 17

**Add-ons reuse step 16's "Free supplies the filter/route, Pro supplies the data" widget-reach shape exactly** — same pattern, but this time the resolved data has a real PRICE consequence, so the read side alone isn't enough; the price itself must never be trusted from the client (the exact class of bug this project already found and fixed once, in Phase 1 step 8's payment-amount tampering gap). **New Free filter** `byzo_resolve_addons( array $resolved, array $addon_ids, int $bookable_item_id )` — default `array()`. A booking request submits only `addon_ids` (an array of ints, no prices); Pro's hook looks up its own `wp_byzo_addons` table, keeping only rows that are `status = 'active'` AND actually requested AND scoped correctly (`bookable_item_id IS NULL` or matches this item) — an id that doesn't resolve (wrong item, inactive, made up) is silently dropped, not an error, same "the real wall answers honestly" shape as every other capacity/availability check in this project. **New Free public route** `GET /addons/public?bookable_item_id=` (widget's own read, same `/public`-suffix convention as `/custom-fields/public`).

**`BYZO_Booking::create()` widened**: right after computing `$subtotal` (unit price × party size, post-`byzo_unit_price`) and before tax, the resolved addons' prices are summed in and a new flat `bookable_items.booking_fee` (if set) is added once per booking (not multiplied by party size — a fee is per-booking, not per-seat). Tax then applies to the WHOLE combined total (subtotal + addons + booking fee), matching how a real invoice taxes every line item, not just the base price. The resolved `[{id, name, price}]` list (server-verified, not the client's `addon_ids`) is what actually gets stored in `bookings.addons` (§1.4, reserved since Phase 0) — a later addon price/name edit in Pro never silently rewrites a past invoice's numbers, same reasoning `payment_amount`/`tax_amount` already freeze at booking time.

**Flat booking/service fee is per-bookable-item config, not site-wide** — shaped exactly like `tax_rate_override` (step 14): a new Free-schema column `bookable_items.booking_fee DECIMAL(10,2) NULL`, no capability gate (purely informational until Pro writes it — Free's own admin screens never expose the field), one dedicated `BYZO_Bookable_Item::update_booking_fee()` setter. Because the fee must be broken out as **its own invoice line, separate from tax** (the FEATURES.md requirement), a snapshot column `bookings.booking_fee_amount DECIMAL(10,2) NULL` freezes the amount actually charged at booking time — reading `bookable_items.booking_fee` live from the confirmation page would show a WRONG number the moment an admin later changes the fee. `BYZO_DB_VERSION` 2.2→2.3 for both new columns.

**New Pro table** `wp_byzo_addons` (§1.6, already speced) — built as originally planned (`id`, `bookable_item_id NULL`, `name`, `price`, `status`), no schema surprises this time. **New Pro REST routes**: `GET/POST /addons` + `PUT/DELETE /addons/{id}` (admin CRUD) and `PUT /bookable-items/{id}/booking-fee` (sets/clears the flat fee, same shape as step 14's tax-rate-override route). **Admin UI**: new "Add-ons & Fees" screen — add-on CRUD list (global or per-item scope, same picker as Form Fields) plus a per-item flat-fee editor reusing the same inline-edit-per-row pattern the Pricing screen's tax-override section already established.

**Widget UI**: `StepDetails.vue` gains a checkbox list of available add-ons (name + price) fetched the same way custom fields are, selected ids collected into `form.addon_ids`; the running total display (already computed client-side as a UX preview, server remains sole authority) adds selected add-on prices so the displayed number doesn't undersell what the server will actually charge. The booking fee is NOT shown as a separate widget-side line before submission (its value lives in Pro's table, unreachable to Free's pre-submit price preview without a data fetch this step doesn't add) — it appears correctly on the post-booking confirmation/email breakdown instead, where the real server-computed `booking_fee_amount` is already available on the created booking record.

**Multilingual booking-facing content stays explicitly out of scope for this step** (unchanged from the original plan) — blocked on §5 item 8's still-open storage-strategy decision (WPML String Translation API vs. a Bookyzo-owned translations table), which this step does not resolve.

### B4/B3/B5. PDF invoice, duplicate booking, post-visit follow-up email — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 18

Three unrelated bullets bundled under one ROADMAP.md batch by history, not by any shared mechanism — each gets its own design below.

**PDF invoice** (§5 item 10 resolved above: dompdf). A new genuine capability, `byzo_pdf_invoice_enabled` (Free, default `false`; Pro overrides `true` while licensed) — genuinely Pro-exclusive infrastructure (a PDF-rendering library only Pro ships), not a re-skin of something Free already does for free, so a real gate is correct here (same class of decision as B9's calendar-feed capability, unlike B3's drag-and-drop reclassification). Free's customer dashboard (`src/account/views/DashboardView.vue`, A11) only renders a "Download invoice" link per booking when `window.byzoAccount.pdfInvoiceEnabled` is true — never a dead/disabled link, matching this project's standing Guideline-5 rule. The link itself is a plain `<a href>` (not a JS fetch+blob dance) pointing at a new Pro-owned REST route, `GET /bookings/{id}/invoice` (no literal `.pdf` — see below), with the REST nonce passed as a `_wpnonce` query param (WordPress's own REST cookie-auth accepts a nonce via query param for exactly this "plain browser-navigable link" case, not only via the `X-WP-Nonce` header) — permission-gated by the same `admin_or_own_customer_permissions_check` reschedule/cancel-as-customer already use. `BYZOP_Invoice_PDF` builds simple branded HTML (business name from `byzo_settings`, booking id/date, customer name/email, an itemized line-item table — base price, each add-on, booking fee, tax, less any deposit already paid, total due) and renders it via `Dompdf\Dompdf`. **Uses the exact `rest_pre_serve_request` bypass this same session just found and fixed missing from B9's calendar feed** (§3 B9's own note above) — built correctly from the start this time, and its own test includes a real `wp_remote_get()` round-trip, not just `rest_do_request()`, specifically because that gap is now a documented, known blind spot for any non-JSON REST route in this project.

**A second, related bug — this time genuinely new to this step, and only catchable by browser verification**: the FIRST draft of `src/account/api.js`'s `getInvoiceUrl()` built the link with a literal `.pdf` URL suffix, matching this design note's own first draft — but the actual REST route (correctly, per the fix above) has no such suffix, since an unescaped `.` in a `register_rest_route()` path is a regex wildcard, not a literal dot. The mismatch 404'd the "Download invoice" link on every real click, invisible to every PHP-level check (`rest_do_request()` tests construct the route path directly, they never exercise the frontend's own URL-building code at all). Fixed by dropping `.pdf` from `getInvoiceUrl()` to match the route; the downloaded file's `.pdf` extension still comes from the `Content-Disposition` header, unaffected either way.

**First-ever third-party PHP dependency, real build-tooling consequence**: `bookyzo-pro/composer.json` (`require: dompdf/dompdf`), `vendor/` committed to source control (unlike `node_modules/`, which stays gitignored) since customer sites never run `composer install` themselves — the plugin must ship the dependency's actual source. `bin/build-release.js`'s `.distignore` (Free's own script, reused as-is for Pro's release zip) needed no change since it already only EXCLUDES a fixed list rather than an allowlist, and `vendor/` was never on that exclude list to begin with — it ships by default, which happens to be exactly correct behavior here.

**Duplicate booking** (`FEATURES.md` B3) — no new Free capability or schema at all: `POST /bookings` has been fully unrestricted since Phase 0 (any admin, or a guest through the widget), so there is nothing to gate, same "no real backend difference to gate" reasoning that reclassified drag-and-drop reschedule to Free in step 11 — except here the ACTION (an admin one-click "duplicate this booking as a starting point") has no Free UI at all to begin with, so it's genuinely new Pro UI, not a re-gate. Lives on Pro's existing "Bulk & Notes" screen (a new "Duplicate" row action) rather than a new screen — Pro cannot inject a button into Free's own already-compiled `BookingsList.vue`/`BookingDetailModal.vue` (the same cross-bundle limitation this project keeps running into), but "Bulk & Notes" is already a Pro-owned table view of the exact same booking data. Clicking Duplicate opens a small Pro-owned modal pre-filled with the source booking's `customer_name`/`customer_email`/`customer_phone`/`customer_notes`/`party_size` (not its `custom_fields`/`addons` — a duplicate is explicitly a fresh starting point, not an exact clone, so per-visit specifics like allergy notes don't silently carry over into an unrelated future visit) and a slot-picker sourced from the existing public `GET /slots?bookable_item_id=`; submitting calls the same unrestricted `POST /bookings` every other booking path already uses. No new REST route.

**Automated post-visit follow-up/thank-you email** (`FEATURES.md` B5) — shaped like Free's own single fixed 24h reminder (`bookings.reminder_sent_at`), not step 7's multi-rule reminder system: FEATURES.md's own wording is "a configurable number of hours" (singular), not multiple independent rules, so a `wp_byzo_reminder_log`-style join table would be over-built for what's actually one setting. New Free-schema column `bookings.followup_sent_at DATETIME NULL` (`BYZO_DB_VERSION` 2.3→2.4, "don't gate the data model" pattern, dormant until Pro writes it) and one new Free method, `BYZO_Booking::get_due_for_followup( DateTime $window_start, DateTime $window_end )` — mirrors `get_due_for_reminder()`'s exact shape but filters on `status = 'completed'` AND `completed_at` inside the window AND `followup_sent_at IS NULL`, rather than a slot's future start time. New Pro settings: `followup_enabled` (bool), `followup_hours` (int, hours after `completed_at`), `followup_subject`/`followup_body` (reuses the existing `{placeholder}` vocabulary via `BYZO_Notifications::build_placeholders()`, same as every other Pro-sent email since step 7). New Pro class `BYZOP_Followup_Email` runs on a new hourly cron `byzop_send_followups` (registered alongside the two existing hourly crons in `BYZOP_Activator::maybe_schedule_cron()`), sending via `wp_mail()` and marking `followup_sent_at` so a booking is never emailed twice even if the cron runs more often than the window moves. **Admin UI**: folds into the existing "SMS & WhatsApp" screen's settings, **renamed "Automated Messages"** (title, subtitle, and nav label all updated) since it now covers more than SMS/WhatsApp — rather than a new screen for three fields: a toggle, an hours input, and a subject/body pair, the smallest possible addition alongside reminder-rule config already living there.

### B4. Per-ticket attendee details — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 20

**A real gap found between ROADMAP.md's own plan and the actual codebase, worth recording**: ROADMAP.md's step 20 text claimed "Free's widget already carries the conditional attendee-name-per-ticket UI... this step is purely: register the filter override" — checked against the actual code before starting (not assumed), and that UI never existed; only the reserved `bookings.attendees` column did. This step is genuinely bigger than its own ROADMAP.md line implied: a new capability, a new widget UI section, AND the write-wiring, not just a filter flip.

**Scope, per `FEATURES.md`'s own wording**: "an EVENT booking with quantity/party size > 1" — scoped to `bookable_item.type === 'event'` specifically, not every type, since the downstream consumer (B7 Event Pro's still-unbuilt attendee list export/QR e-tickets) only exists for that type. New genuine capability `byzo_collect_attendee_details` (Free, default `false`; Pro overrides `true` while licensed) — exposed once, site-wide, via `window.byzoWidget.collectAttendeeDetailsEnabled` (same shape `customerAccountsEnabled`/`taxRate` already use) rather than a per-request fetch, since it's a plain boolean setting with no per-bookable-item variation.

**Widget UI**: `StepDetails.vue` shows an "Attendee details" section — one row per ticket (name required, email optional) — only when the capability is on AND `item.type === 'event'` AND the effective quantity is > 1; a `watch()` on the resolved quantity keeps `form.attendees` sized correctly as party size changes (growing adds blank rows, shrinking truncates) rather than locking in a count chosen too early. No new REST route: `POST /bookings` already passes its whole JSON body through to `BYZO_Booking::create()` unchanged, the same reason `custom_fields`/`addon_ids` needed no route wiring either.

**Deliberately not built this step, flagged not silently dropped**: the actual "feed into B7 Event Pro's attendee list export and QR e-ticket generation" (ROADMAP.md's own step 20 wording) doesn't happen yet, because Event Pro itself — the type-module this data ultimately feeds — is still one of the two large deferred modules at the end of Phase 2. Collection is enabled now so the data exists retroactively once Event Pro is eventually built, rather than making every event booking between now and then permanently missing attendee data.

### B7 (Table). Floor plan editor, combine/split tables, walk-in waitlist — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 12 (continued)

The last unbuilt B7 type-module bullet set besides Event, picked up now (Table before Event, continuing step 12's own "smallest first" reasoning — Table needs no new third-party dependency, Event needs QR generation/scanning). **One bullet already fully covered before this step started, confirmed not assumed**: `FEATURES.md`'s "multiple service windows per day" bullet is the SAME capability as `byzo_max_shifts_per_day` — Free's own Table description (§A2/§A9) literally says "single service window (one shift/day)," and Pro already removed that cap universally (step 2/3), Table included. Nothing to build.

**Visual floor plan / table layout editor.** Position is purely visual — it changes nothing about booking/slot/capacity logic, only how the admin screen draws Table-type bookable items relative to each other — so it fits the exact same shape as `tax_rate_override`/`commission_type`: new Free-schema columns on `bookable_items` (`floor_x`/`floor_y`/`floor_width`/`floor_height SMALLINT NULL`, `floor_shape VARCHAR(20) NULL`), no capability gate on the data itself, Free's own admin never exposes them. `BYZO_DB_VERSION` bump. One new Free method, `BYZO_Bookable_Item::update_floor_position()`. **Editor UI reuses the exact native-HTML5-drag-and-drop technique step 11's calendar drag-and-drop reschedule already proved out** in this codebase (absolute-positioned elements inside a relatively-positioned canvas `<div>`, `dragstart`/`dragover`/`drop` — no canvas library, no new dependency) rather than inventing a new interaction pattern. New Pro REST route `PUT /bookable-items/{id}/floor-position`.

**Combine/split tables for larger parties.** Reframed as one capability, not two: "combine" (party bigger than any single table) and "split" (spread one reservation across tables) are the same underlying need — a booking backed by more than one physical table. Deliberately does NOT invent a new grouping table: the PRIMARY table holds the real booking (with the combined `party_size`), and each ADDITIONAL table's overlapping slot is flipped to `'blocked'` — reusing the exact slot-blocking mechanism blackout dates/calendar-sync already established (`wp_byzo_slots.status`), so a combined-away table simply can't be double-booked without any new capacity logic. A new Free-schema column `bookings.combined_table_ids VARCHAR(255) NULL` (comma-separated bookable_item_ids) records which OTHER tables are part of the combo, so un-combining (or the booking being cancelled) knows exactly which slots to unblock — same "don't gate the data model" pattern, no capability check on the column itself, only Pro's own combine/split UI action ever writes it. New Pro REST route `POST /bookings/{id}/combine-tables` (body: `{table_ids: [...], slot_ids: [...]}`) and `POST /bookings/{id}/uncombine-tables`.

**Walk-in waitlist.** Genuinely distinct from B2's still-unbuilt general "notify when a slot frees up" waitlist (§3 B2, `wp_byzo_waitlist` — that one's about a FUTURE slot; this one has no slot at all, a physical queue for right-now arrivals) — new Pro-only table `wp_byzo_walkin_waitlist` (`id`, `bookable_item_id NULL` — global across every Table-type item, since a walk-in isn't tied to one specific table upfront, `customer_name`, `customer_phone`, `party_size`, `status` [`waiting`/`seated`/`left`/`no_show`], `joined_at`, `seated_at NULL`). New Pro REST CRUD + a new "Waitlist" admin screen (add walk-in, live queue sorted by `joined_at`, one-click seated/left).

**Deliberately deferred, flagged not silently dropped**: a genuine floor-plan-editor "seating chart" for Event Pro (`FEATURES.md` explicitly marks it "(optional)" even in the original spec) reuses this same floor-plan mechanism once built, but isn't built proactively here — no concrete Event-side need yet. The general B2 slot-notification waitlist (`wp_byzo_waitlist`, DETAILED-SPEC.md §3 B1/B2's own early design note) stays unbuilt — it was never assigned to any numbered ROADMAP.md step (only Table's walk-in waitlist was, under step 12), so building it now would be unscoped extra work, not a gap in step 12 itself.

**Confirmed built and verified 2026-09-12, 77 automated checks (`smoke-phase2-step12-table.php`) plus a real headless-Chrome pass over Floor Plan/Waitlist/Bulk & Notes**: everything above shipped exactly as designed, with one refinement made during the build — `combine_tables()` gained a 4th optional `$party_size` parameter (REST body key `party_size`) so the "primary table holds the combined party_size" promise above is actually reachable from the UI in one action, rather than requiring a second, currently-nonexistent "edit party_size" route (Free's own `PUT /bookings/{id}` is status-change-only; there was never a party_size-editing route to lean on, so the original design's "same as any other edit" phrasing was corrected here rather than shipped as a dead end). `combine_tables()` rolls back every slot it already blocked in the same call if a later one in the list turns out unavailable (no wrapping DB transaction elsewhere in this project either, so this is the established pattern). The Floor Plan editor's drag-and-drop is native HTML5 (`dragstart`/`dragover`/`drop`) exactly as planned, free-form (absolute x/y) rather than grid-snapped like the calendar's own drag-to-reschedule, since a floor plan has no fixed grid; a table with no saved position yet gets a client-side-only default grid slot purely for rendering, never written until actually dragged or edited. Real bug found only by the browser pass (never by the 74 PHP-only checks, which don't exercise a live DOM): a fixed drag-drop target coincided with wherever a PRIOR test run's own drag had already left the table (the position genuinely persists server-side, which is the feature), producing a same-position false negative that looked like broken drag-and-drop but wasn't — fixed in the verification script itself (a random in-canvas target) once diagnosed, not a product bug.

### B7 (Event). Ticket tiers, QR e-tickets, web check-in scanner, attendee export — DESIGNED + BUILT 2026-09-12, ROADMAP.md Phase 2 step 12 (continued, final type-module — Phase 2 exit criteria met)

The last unbuilt B7 type-module. Four real bullets (seating chart stays deferred, same call already made in the Table section above — no concrete need yet, reuses the floor-plan mechanism once one exists).

**Ticket tiers with per-tier pricing.** Mirrors step 5's "services" shape almost exactly: a new Pro-owned table `wp_byzo_ticket_tiers` (`id`, `bookable_item_id`, `name`, `price`, `capacity`, `capacity_remaining`, `sort_order`, `status`) plus a new Free-schema column `bookings.ticket_tier_id BIGINT UNSIGNED NULL` (don't-gate-the-data-model pattern — Free's own widget never renders tier selection without Pro's filter supplying tiers, so the column stays permanently NULL on an unlicensed install). Capacity is enforced at TWO levels simultaneously, both atomic UPDATEs: the event's own slot `capacity_remaining` (already enforced, unchanged) AND, when a tier is selected, the tier's own `capacity_remaining` — a new filter `byzo_claim_ticket_tier( $claimed, $ticket_tier_id, $party_size )` (default no-op / `null` = "no tier system installed, nothing to claim") called from `BYZO_Booking::attempt_create_on_slot()` right after the slot's own claim succeeds; if the tier claim fails (sold out), the slot's own claim is rolled back (capacity_remaining incremented back, mirroring `combine_tables()`'s own just-established rollback pattern) and `byzo_tier_sold_out` is returned. Price resolution reuses the `byzo_service_price`-style shape: a new filter `byzo_ticket_tier_price( $price, $ticket_tier_id )` resolves the tier's own price, checked before the bookable item's flat `price` (same precedence order services already established over a flat price). Widget reach follows the exact step 16/17 shape: new Free filter `byzo_ticket_tiers_for_bookable_item` (empty without Pro) + new public route `GET /ticket-tiers/public?bookable_item_id=`, so `StepDetails.vue` can render a tier picker only when tiers actually exist for that event. New Pro admin-only CRUD REST routes + a "Ticket Tiers" admin screen (tier list per event, add/edit modal).

**QR e-tickets.** Deliberately ONE ticket per booking, not one per attendee — nothing in `FEATURES.md`'s wording requires per-seat scanning, and step 20's `attendees` array already exists for name-level detail without needing a QR per name; over-building granularity nobody asked for is the same mistake this project has avoided everywhere else (addons' no-quantity-multiplier call, deposits' simple percentage-or-fixed shape). A new stateless-HMAC sibling `BYZO_Ticket_Token` (same `wp_salt('auth')` shape as `BYZO_Booking_Token`/`BYZO_Calendar_Feed_Token`, scoped to just `booking_id` — a host scanning at the door has no reason to also need the customer's email) backs a new Pro-owned route `GET /bookings/{id}/ticket-qr`, admin-or-owning-customer gated exactly like the PDF invoice route, streaming a PNG QR image encoding `{booking_id, token}` as its payload. **QR generation library decision: `chillerlan/php-qrcode` via Composer** (added alongside the existing `dompdf/dompdf` dependency, same "customer sites never run `composer install`, `vendor/` is committed" reasoning already established in step 18) — MIT-licensed, actively maintained, needs only GD (already available), no Imagick requirement unlike some alternatives. **Must use the `rest_pre_serve_request` bypass from the start** (the mandatory pattern this project learned the hard way in step 15/18 — `WP_REST_Server::serve_request()` always JSON-encodes otherwise) since this is the second non-JSON-streaming route in this codebase after the invoice PDF. **Web check-in scanner.** A new Pro admin screen, "Check-in" — camera-based, no native app, matching `FEATURES.md`'s explicit "web-based, no app needed" requirement. **QR *scanning* library decision: `jsqr` via npm** (Pro's admin Vue app already has Vite/npm build tooling; `jsqr` is a small, dependency-free, actively-maintained JS QR decoder — no CDN dependency, no native binary, distinct choice from the PHP generation side since decoding happens entirely client-side against `getUserMedia` camera frames sampled onto an offscreen `<canvas>`, never sent to the server as an image). ### B9. WooCommerce Bridge — DESIGNED + BUILT 2026-09-13, ROADMAP.md Phase 5 (all 5 steps complete)

**Positioning.** A **third, separate plugin** — `bookyzo-woocommerce` (prefix `BYZOWC_`/`byzowc_`, matching the `BYZO_`→`BYZOP_` pattern), not a module bundled into `bookyzo-pro`. Most Bookyzo sites don't run WooCommerce at all, so the bridge shouldn't be dead weight inside core Pro; FEATURES.md Part C step 6's own wording ("separate optional add-on") reads as *separate plugin install*, not a separate purchase — B9 already lists the WC bridge in the same bullet list as webhooks/Zapier/Google Calendar sync (already shipped inside `bookyzo-pro`, Phase 2 step 15), so it stays gated by the same Pro license rather than standing up a second license-server product for one feature. **Dependency chain**: `bookyzo-woocommerce` requires `bookyzo` (Free, booking engine) + `bookyzo-pro` active AND licensed (`byzop_is_licensed()`, same check every other B9 feature uses) + WooCommerce active — admin notice + graceful no-op if any is missing, same convention `bookyzo-pro` already follows toward `bookyzo`.

**Schema boundary — DECIDED 2026-09-13 (user): `wc_order_id` column, not a separate mapping table.** New nullable `wp_byzo_bookings.wc_order_id` column (`BYZO_DB_VERSION` bump) — one booking, one WC order, matching every other single-FK column already on this table (`customer_id`, `cart_id`) rather than join-table machinery for a relationship that's 1:1 in practice (an order created by Bookyzo's own checkout flow always corresponds to exactly one booking — WC's own multi-item cart can still hold unrelated products alongside it, untouched). **This column lives on Free's own table, not the bridge plugin's** — same "don't gate the data model" precedent as `tax_amount`/`cart_id`/`attendees` before Pro ever consumed them, so a future Free release never needs a migration just because the bridge added a column.

**Product mapping**: new nullable `wp_byzo_bookable_items.wc_product_id` column, also Free-schema. `BYZOWC_Product_Sync` (bridge-owned) creates one hidden, virtual WC simple product per WC-bridge-enabled bookable item, synced on save (name, `byzo_unit_price`-filtered price so Pro's seasonal/deposit pricing still applies), `_virtual` = yes (no shipping), `catalog_visibility` = hidden (never appears in the WC shop/search — Bookyzo's own widget stays the only real entry point). Bookable-item-side `wc_product_id` and product-side `_byzo_bookable_item_id` postmeta point at each other.

**Checkout flow — the actual bridge.** When enabled for a bookable item, the public widget's final step swaps Bookyzo's own inline Stripe/PayPal step for "add to WooCommerce cart → redirect to WC checkout":
1. `BYZO_Booking::create()` runs exactly as it already does for a direct booking — status `pending`, capacity atomically claimed the same way every booking type already claims it. No new booking-creation code path.
2. `WC()->cart->add_to_cart( $wc_product_id, 1, 0, array(), array( 'byzo_booking_id' => $booking_id ) )` — the booking id rides as cart-item meta, not a new lookup table.
3. `woocommerce_order_status_changed` to `processing`/`completed` → `BYZOWC_Order_Sync` reads `byzo_booking_id` off the matching order line item, calls the same `BYZO_Booking::update_status( $booking_id, 'confirmed' )` every other gateway's webhook already calls, and stamps `wc_order_id`.
4. Order `cancelled`/`failed`/`refunded` → booking cancelled, capacity released — same existing cancel path.

**New: stale-pending-booking cleanup — genuinely new infrastructure this phase needs, flagged rather than silently added elsewhere.** WC's own multi-step checkout (cart → address → payment, real page loads) is a longer, leakier abandonment window than the widget's own single-page Stripe/PayPal flow, and **no expiry mechanism for an unpaid `pending` booking exists anywhere in Bookyzo today** — a direct Stripe booking that's never paid currently holds its slot's capacity forever. This phase adds one: a new hourly cron `byzo_release_stale_pending_bookings` (Free-owned — the gap is real regardless of the WC bridge, the bridge just makes it likely to matter first) auto-cancels any `pending` booking older than a new `byzo_settings['pending_booking_hold_hours']` (default 24h) with no successful payment, releasing its slot capacity through the existing cancel path.

**Free/Pro split of the bridge itself**: none — the whole plugin is Pro-gated per the dependency chain above; there's no free tier of "use WooCommerce checkout." This differs from every other Pro module in this project (which all extend an already-working Free feature) — the bridge instead REPLACES a working Free feature (direct Stripe/PayPal) with a WC-routed equivalent for bookable items that opt in, which is why it's a swap in the widget's final step rather than an additional always-available option.

**Deferred, flagged not silently dropped**: WC coupon/discount-code passthrough (B6 already lists coupons as its own bullet — whether WC's own coupon UI double-serves that or Bookyzo needs its own is a later question); WC Subscriptions integration for B6's "package/membership pre-purchase" bullet (a different WC extension entirely).

### B2–B11, general pattern
Same pattern throughout for everything not called out above: Pro adds its own tables/columns where the feature is genuinely Pro-exclusive data (floor plan layout, ticket tiers, SMS logs, revenue rollups), and consumes Free's filter/action hooks where it's extending Free's existing flow (booking status changes, notification events, settings UI sections). **Full hook inventory should be written as each Free feature is built**, not speculated now — CBFW's real hook list (`bpfw_settings_sections`, `bpfw_default_settings`, etc.) only emerged feature-by-feature during actual implementation. Placeholder hook names to reserve conceptually: `byzo_booking_status_changed`, `byzo_settings_sections`, `byzo_default_settings`, `byzo_notification_events`, `byzo_can_book_bookable_item` (capability filter, mirrors CBFW's `cbfw_can_bundle_product` fix — a real capability check, never a hardcoded array allowlist).

## 5. Open Decisions (resolve before/at start of coding, not mid-build)

1. **Timezone storage — DECIDED 2026-09-02: site-local.** All `DATETIME` columns (`wp_byzo_schedules.start_time`/`end_time`, `wp_byzo_availability_exceptions.date`/`start_time`/`end_time`, `wp_byzo_slots.start_datetime`/`end_datetime`, `wp_byzo_bookings` timestamps) store the WordPress site's configured local time (`wp_timestamp`/`current_time('mysql')`, matching core WP convention and most small WP booking plugins), NOT UTC. Consequence to design around: since Bookyzo is single-location on Free, this is safe. Once Pro's multi-location feature (B1) ships with per-location timezones, slot generation/display for a non-default-timezone location needs explicit conversion at read/write time (via `wp_timezone()`/`get_option('timezone_string')` per location) — the DB column itself still just holds a naive local datetime for that location, so the location's own timezone must always travel alongside any datetime read from `wp_byzo_slots`/`wp_byzo_bookings`, never assumed to be the site default. Flag this explicitly when B1/multi-location work starts.
2. **Which booking type ships first** — **DECIDED 2026-09-02: Appointment** as the reference implementation (built first, complete). ~~Table/Event/Slot not built until launch step 4~~ — **SUPERSEDED same day by item 5 below**: the other three types now go into Free BEFORE the first WP.org submission.
3. **Slug/prefix finality**: `bookyzo` / `BYZO_` used throughout this doc is a first pass, following the CBFW precedent of picking something short and renaming later only if WordPress.org's reviewer flags genericness — do not treat `BYZO_` as sacred if a review round asks for a change (see [[bundle-product-plugin]]'s full prefix-rename history for what that process looks like).
4. **WooCommerce bridge boundary** (B9): **RESOLVED 2026-09-13 — `wc_order_id` column on `wp_byzo_bookings`** (user decision), not a separate mapping table. Full design in §3's "B9. WooCommerce Bridge" section.
5. **All four booking types in Free — DECIDED 2026-09-02 (user direction change).** Appointment + Table + Event + Slot all ship in the Free plugin before the first WordPress.org submission; Pro gates extra features only, never booking types. Free's volume cap = one active bookable item per type (`max_bookable_items_per_type`, unchanged). The never-enforced `max_active_bookable_item_types()` capability is to be deleted (see §A9). Build order for the remaining work: `ROADMAP.md` Phase 1.5.
6. **Type-first creation UX + per-bookable item shortcodes — DECIDED 2026-09-02 (user).** "Add New" bookable item flow picks the booking type FIRST, then shows a type-specific form (field matrix in §A2/A3); every bookable item's own pinned shortcode (`[bookyzo_booking bookable_item_id="X"]`) is displayed copyable in the Bookable Items list, plus a `type=""` shortcode/block variant for a type-filtered picker.
7. **Event occurrence model — DECIDED 2026-09-02: direct slot rows, no weekly schedule.** Event-type bookable items skip `wp_byzo_schedules`/the generator entirely; admin-entered occurrences are written straight into `wp_byzo_slots` (full rationale in §1.3). Chosen over adding event-date columns to the bookable items table because it needs zero schema change and reuses the whole existing booking/capacity path.
8. **Multilingual booking-facing content storage — OPEN, added 2026-09-03 (competitor gap-fill, B11).** Bookable Items/services aren't WP posts (§1, custom DB tables by design), so WPML/Polylang's normal post-based translation UI won't pick them up automatically the way it would a CPT. Two real options, not yet chosen: **(a)** register each translatable string via WPML's String Translation API (`icl_register_string`/the `wpml_register_string` action) at save-time, letting WPML's own String Translation screen manage the actual translated values — less new code, but ties the feature to WPML specifically and String Translation's UX wasn't built for a growing list of per-bookable item strings; **(b)** a Bookyzo-owned `wp_byzo_bookable_item_translations` table (`bookable_item_id`, `locale`, `name`, `description`) with Bookyzo's own admin UI for editing per-language values — more upfront work, but plugin-agnostic (works without WPML/Polylang installed at all) and fits this doc's existing "own the data model" pattern better. Resolve this before B11 implementation starts, not mid-build — whichever is chosen changes both the schema (§1.6 would need a new table for option b) and the Bookable Item admin screen's Details tab layout.
9. **Linked/combined resource availability — FLAGGED, NOT ADOPTED (added 2026-09-05, Universal-Booking-Plugin gap audit).** The user-supplied wishlist described a bookable item needing a second entity free at the same time — e.g. a doctor AND an exam room, or a table AND a specific server — genuinely different from today's model, where one bookable item IS the one thing being checked for availability. Adopting this needs a `wp_byzo_resource_links` join table plus multi-entity availability-intersection logic in `BYZO_Slot_Generator`/booking creation (checking N calendars at once, not one) — a bigger architectural lift than a normal Pro feature, closer in scope to the "Custom Booking Type" idea this doc already declined to adopt without an explicit decision (see the `FEATURES.md` callout at the top of that doc). **Not built, not scheduled in `ROADMAP.md`.** Flag to the user and get an explicit decision before starting, same as item 8 above.
10. **PDF invoice generation — RESOLVED 2026-09-12, Phase 2 step 18: option (a), dompdf via Composer.** Option (b) (headless-Chrome-style rendering) was ruled out on inspection, not just in theory: it needs a Chrome/Node runtime present on the SAME machine serving the request, which today only exists as a one-off dev-time tool on this dev box — the overwhelming majority of real WordPress hosting (shared hosting especially) has no such runtime available server-side, so a live customer site could not reliably generate an invoice on demand. dompdf is pure PHP, runs anywhere PHP already runs, and only needs `vendor/` shipped alongside the plugin (no Composer required on the customer's own site — `composer install` happens once at build time in this repo, same "compile ahead, ship the output" shape `npm run build`'s `assets/` output already uses for JS/CSS). This IS the plugin's first-ever third-party PHP dependency; `bin/build-release.js`'s `.distignore` needed one exception added (`vendor/` is normally dev-tooling-shaped and would otherwise be excluded like `node_modules/`, but here it must ship, since dompdf isn't compiled into a bundle the way Vite compiles JS).
11. **Widget view tracking for conversion rate — OPEN, added 2026-09-05 (B8).** "Conversion rate" (widget views → completed bookings) needs some view-counter; nothing today records a widget impression, only completed `POST /bookings` calls do. A naive ping-on-mount is easy to build but adds a new public write endpoint with its own abuse-guard question — same shape as `BYZO_Public_Guard`'s existing honeypot/rate-limit on booking creation, but for a much higher-volume, lower-value event, so the same rate-limit numbers likely don't just carry over unchanged. Resolve the tracking mechanism before B8's conversion-rate metric is built (`ROADMAP.md` Phase 2 step 19 depends on this).
