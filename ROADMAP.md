# Bookyzo — Build Roadmap

Ordered, dependency-aware step list: what to build, and in what sequence, from zero to the full multi-type Pro product. Companion to `FEATURES.md` (what) and `DETAILED-SPEC.md` (how/schema). This file answers **"which step comes after which."**

Scope for now: **Phase 0–2** is the actionable near-term plan. Phases 3+ are sequenced but intentionally light on detail — per `FEATURES.md` Part C's own principle, don't over-plan stages that are months away.

> **DIRECTION CHANGE 2026-09-02:** all four booking types (Appointment + Table + Event + Slot) go into **Free** before the first WordPress.org submission; Pro gates extra features only, never types. This adds **Phase 1.5** below, supersedes the old Phase 3/4 (second/third type phases), and rewrites one row of the conversion table. `FEATURES.md` Part C and `DETAILED-SPEC.md` §5 items 5–7 carry the same change.

> **COMPETITOR GAP-FILL 2026-09-03:** 17 items added to `FEATURES.md` after auditing Bookly, Booking Calendar, and Amelia feature-by-feature. Adds one step to **Phase 1.5** (step 9, Free-tier items) and four steps to **Phase 2** (steps 13–16, Pro-tier items), plus two new conversion-table rows below. Full schema/API detail in `DETAILED-SPEC.md` §1.5/§1.6/§4; one genuinely open architecture question (multilingual content storage) in `DETAILED-SPEC.md` §5 item 8.

> **ONBOARDING & DASHBOARD DEEPENED 2026-09-03:** user-supplied wizard+dashboard UX spec, reconciled against Bookyzo's decided architecture (see `FEATURES.md`'s callout for the 3 deviations — 4 types not 7/no custom type, Availability stays bookable item-scoped, Free gets one Revenue total not a breakdown) and one genuinely new setting (auto-confirm vs. manual approval). Rewrites **Phase 1.5 step 6** (the wizard, now 5 in-wizard steps + review + success instead of 3 steps) and adds **Phase 1.5 step 10** (Dashboard + admin nav enrichment).

> **NAMING: "resource" → "bookable item" (2026-09-03, user-directed).** "Resource" read as an unclear, overly technical term to an end user (what does a business owner think a "resource" is?) — renamed everywhere, not just the UI label: DB table (`wp_byzo_resources` → `wp_byzo_bookable_items`, `resource_id` columns → `bookable_item_id`, real migration for pre-existing installs, `BYZO_DB_VERSION` → `1.3`), PHP classes (`BYZO_Resource` → `BYZO_Bookable_Item`, `BYZO_REST_Resources_Controller` → `BYZO_REST_Bookable_Items_Controller`), REST routes (`/resources` → `/bookable-items`), hooks/filters, shortcode/block attributes, every Vue component under `src/views/resources/` → `src/views/bookable-items/`, and this whole doc set (`FEATURES.md`/`DETAILED-SPEC.md`/`ROADMAP.md`/`readme.txt`/both skill files). Full regression suite (25 scratchpad smoke tests) and both Vite bundles verified clean after the rename. Every step below already reflects the new terminology — this note exists so the history of *why* isn't lost, not because any step needs re-reading differently.

## Phase 0 — Core Engine (no public release)

Nothing here is type-specific. Build once, every booking type reuses it.

1. ✅ **DONE (2026-09-02)** — Plugin bootstrap: main file header, activation/deactivation hooks, `dbDelta` schema installer for the 4 core tables (`wp_byzo_bookable_items`, `wp_byzo_schedules`, `wp_byzo_availability_exceptions`, `wp_byzo_slots`, `wp_byzo_bookings` — see `DETAILED-SPEC.md` §1), `byzo_settings` option defaults, uninstall cleanup. Also added: `BYZO_Capabilities` (the real capability-filter layer per the Guideline-5 rule, e.g. `max_bookable_items_per_type()`/`max_shifts_per_day()`), setup-wizard activation-redirect scaffold (`BYZO_Install_Redirect`), placeholder admin menu page (Vue mount point for step 7), and DB-version-bump upgrade path in `BYZO_Plugin::maybe_upgrade_db()`. Verified via two scratchpad smoke tests: raw `BYZO_Activator::activate()` (table/column/settings checks) and a full-flow test through WP's own `activate_plugin()` + `plugins_loaded` (confirms hook wiring, capability filter override, clean deactivation). All passed.
2. ✅ **DONE (2026-09-02)** — REST API skeleton: namespace `bookyzo/v1`, auth/capability checks per route, base controller class pattern. Added `BYZO_REST_Controller` (abstract base — `NAMESPACE_V1` constant, `admin_permissions_check()` for capability-gated routes, `public_permissions_check()` reserved hook point for the guest-widget abuse guard per DETAILED-SPEC.md §4) and `BYZO_REST` (registers on `rest_api_init`, collects concrete controllers via the `byzo_rest_controllers` filter so Pro adds its own controllers without patching Free). Verified via `scratchpad/smoke-rest-skeleton.php`: a throwaway test controller registered through the real filter chain, confirmed route registration, 401 for unauthenticated requests, and 200 for an admin request — the full chain concrete controllers will use starting step 3.
3. ✅ **DONE (2026-09-02)** — `/bookable-items` CRUD endpoint + `/bookable-items/{id}/availability` endpoint (schedules + exceptions). Added `BYZO_Bookable_Item` (data-access layer over `wp_byzo_bookable_items` — validate/create/update/delete/query with type+status filtering and pagination), `BYZO_Availability` (over `wp_byzo_schedules` + `wp_byzo_availability_exceptions` — full-weekly-schedule replace, blackout exception add/delete), and `BYZO_REST_Bookable_Items_Controller` (all routes: `GET/POST /bookable-items`, `GET/PUT/DELETE /bookable-items/{id}`, `GET/PUT /bookable-items/{id}/availability`, `POST /bookable-items/{id}/availability/exceptions`, `DELETE .../exceptions/{id}`). Both the Free "1 active bookable item per type" cap (§A9) and the Free "1 shift/day" cap (§A3/§1.2) are enforced here as real, filterable capability checks (`byzo_max_bookable_items_per_type`, `byzo_max_shifts_per_day`) — confirmed blocking on Free defaults AND unblocking under a simulated Pro filter override, per two scratchpad smoke tests (`smoke-bookable-items-crud.php`, `smoke-availability.php`, 19 checks total, all passed) exercising the real REST dispatcher end-to-end (create/read/update/delete, validation errors, cap enforcement, auth).
4. ✅ **DONE (2026-09-02)** — Slot generator (`BYZO_Slot_Generator`): weekly schedule × exceptions × buffer × min/max advance window → rows in `wp_byzo_slots`. Cron registration (`byzo_generate_slots` daily, plus `byzo_send_reminders` hourly reserved for Phase 1's reminder emails), idempotent upsert logic (`ON DUPLICATE KEY UPDATE`, keyed on the `bookable_item_id + start_datetime` unique index from step 1). Also: (a) discovered and fixed a schema gap — `wp_byzo_bookable_items` had no `duration_minutes` column despite DETAILED-SPEC.md §A9 saying Free is "fixed duration"; added it (default 30, user decision 2026-09-02) and bumped `BYZO_DB_VERSION` to `1.1` so `BYZO_Plugin::maybe_upgrade_db()` picks it up on existing installs; (b) blackout exceptions now actively flip already-materialized `open` slots to `blocked` (`BYZO_Slot_Generator::block_slots_on_dates()`) rather than only skipping future generation — a blackout added after slots already exist would otherwise leave stale bookable slots; (c) bookable item create, availability schedule updates, and exception adds all trigger immediate regeneration for that bookable item (`byzo_bookable_item_created` action + direct calls) so a business doesn't wait up to 24h for the next cron tick to see a bookable widget. Verified via `scratchpad/smoke-slot-generator.php` (12 checks: duration/buffer slot math, idempotent re-run, blackout blocking without duplicating/deleting rows, cron registration, min-advance-notice cutoff) — all passed, plus both earlier smoke test suites re-run clean (no regressions from the schema change).
5. ✅ **DONE (2026-09-02)** — `/slots` public read endpoint (filtered by bookable item + date range). Added `BYZO_Slot` (read-only data layer — date-range query defaulting `from`=today/`to`=`max_advance_days` out, `open_only` filter requiring `status='open' AND capacity_remaining>0`, the shape the public booking widget needs) and `BYZO_REST_Slots_Controller` (`GET /slots?bookable_item_id=&from=&to=`, gated by `public_permissions_check()` — the guest-allowed permission callback reserved in step 2, not `admin_permissions_check()`). Inactive/archived/non-existent bookable items all return the same 404 rather than leaking bookable item-status via a different error shape. Verified via `scratchpad/smoke-slots-endpoint.php` (8 checks: unauthenticated/guest access succeeds, slot shape + duration correctness, validation errors, 404 on missing/inactive bookable item, date-range narrowing, full-capacity slots excluded from results) — all passed, plus all 3 earlier smoke suites re-run clean.
6. ✅ **DONE (2026-09-02)** — `/bookings` endpoint: POST (create, guest-allowed) + GET (admin list) + PUT (status transition state machine). Added `BYZO_Booking` (data layer + `TRANSITIONS` state machine table — `pending→{confirmed,cancelled,no_show}`, `confirmed→{completed,cancelled,no_show}`, `completed`/`cancelled`/`no_show` all terminal, matching DETAILED-SPEC.md §A4 exactly) and `BYZO_REST_Bookings_Controller` (`POST /bookings` via `public_permissions_check()` — same route the admin manual-booking modal will call later, just with an authenticated request instead of a guest one; `GET`/`PUT` via `admin_permissions_check()`). Booking creation atomically decrements `wp_byzo_slots.capacity_remaining` with a single conditional `UPDATE ... WHERE capacity_remaining >= party_size` (no read-then-write gap), flips the slot to `full` at zero, and rolls the slot back to `open`/credits capacity on cancel or no-show — never on completion (capacity being taken reflects the appointment having happened). Verified via `scratchpad/smoke-bookings.php` (15 checks: guest create, atomic decrement, double-booking blocked with 409, full state-machine incl. the illegal `completed→pending` reversal DETAILED-SPEC.md explicitly calls out, cancel-releases-capacity, admin GET filters, auth gating) plus `scratchpad/smoke-bookings-race.php` — a **real concurrency test** (8 simultaneous HTTP requests via `curl_multi` against the live XAMPP server, not simulated) confirming exactly 1 of 8 wins a capacity-1 slot and the other 7 get 409, proving the atomic-UPDATE guard holds under actual concurrent load, not just sequential calls. All 4 earlier smoke suites re-run clean.
7. ✅ **DONE (2026-09-02)** — Vue 3 admin shell: build tooling (Vite), mount point in wp-admin, router skeleton with one placeholder route, `wp.apiFetch` wrapper talking to the REST API above. `admin/` is a self-contained Vite+Vue 3 project (`package.json`, `vite.config.js` with `manifest: true`, `src/main.js` → `App.vue` → `vue-router` hash-history skeleton → placeholder `Dashboard.vue`), styled from the `bookyzo-design` skill's exact token set (`src/styles/tokens.css`, brand `#2563eb`). `src/api/client.js` wraps `window.wp.apiFetch`, scoped to the `bookyzo/v1` namespace. PHP side: `BYZO_Admin_Assets` reads `admin/dist/.vite/manifest.json` (no hardcoded hashed filenames on either side of the build boundary) and enqueues the built script/style **only** on `toplevel_page_bookyzo` — never site-wide — plus injects the REST nonce + root-URL middleware wp.apiFetch needs via `wp_add_inline_script`. Falls back to an admin notice (not a fatal) if the app hasn't been built yet. Verified via `scratchpad/smoke-admin-assets.php` (7 checks: manifest parsing, correct conditional enqueue, hashed-filename match, no enqueue on unrelated admin pages, middleware inline script present, mount-point div rendered) plus a real `npm run build` producing a working bundle (89KB JS / 0.85KB CSS gzipped ~35KB) and a live-server HTTP sanity check (no fatal error on `admin.php?page=bookyzo`, correct 302 login redirect for an unauthenticated request). **Not yet verified: an actual logged-in browser render** (Vue mounting, the Dashboard's live REST round-trip) — no browser automation tool was available this session; left the plugin active for the user to confirm visually.
   - **Dev workflow note**: `npm install && npm run build` (or `npm run dev` for local iteration) run manually from the **plugin root** — this is a Node build step outside PHP's world, matching how `bookyzo-design`'s shadcn-vue CLI additions will also need to be run manually as screens are built in Phase 1.
   - **File layout — FINAL as of 2026-09-02 (went through three revisions, all user-directed — do not "simplify" this back to a nested `admin/src`/`admin/dist` layout, nor move the build output back up to root-level `admin/`/`public/`; both were deliberately rejected):**
     - **Plugin root**: `package.json`, `node_modules/`, `vite.config.js`, `tailwind.config.js`, `postcss.config.js`, `components.json` — one npm project for the whole plugin. All dev-only, excluded from the eventual WordPress.org release zip (Phase 1 step 10).
     - **`src/`** (plugin root level): Vue source — never ships.
     - **`assets/admin/`**: the admin app's Vite **build output directly** (`assets/admin/.vite/manifest.json`, `assets/admin/assets/*.js,*.css`) — NOT `assets/admin/dist/`. **`assets/widget/`** is the mirror of it for the public booking widget. Every shipped static file lives under `assets/`, so the plugin root stays PHP-only (`includes/`, `templates/`, `blocks/`, `assets/`) with no build-output folder sitting beside them — the `backreload` plugin's `assets/dist/` layout is the precedent. These two folders are exactly what a running site needs and exactly what the release zip includes.
     - **Admin routing**: each admin screen is a real registered WP page with its own slug (`bookyzo`, `bookyzo-calendar`, `bookyzo-bookings`, `bookyzo-bookable-items`, `bookyzo-emails`, `bookyzo-payments`) — `BYZO_Plugin::routes()` is the single source of truth mapping slug → Vue route. `BYZO_Admin_Assets` reads the requested slug and hands the booting app its start route in `window.byzoAdmin.initialRoute`; `src/router/history.js` rewrites the `page` parameter on navigation so WP's own left-nav highlighting stays correct, and sub-routes with no page of their own (`/setup`, `/bookable-items/new`, `/bookable-items/:id/edit`) ride on their section's page via a `view` parameter. **Do not** move back to the single-`page=bookyzo`-plus-`view=` scheme this replaced (user-directed 2026-09-02, `backreload` cited as the precedent): with one shared slug WP cannot tell the submenu rows apart and never highlights the active one.
     - Both are **gitignored** (standard practice — build output isn't source-controlled) — a fresh `git clone` needs either `npm run build` (production) or `npm run dev` (dev-mode, see below) before the admin panel renders.
     - **Dev mode**: `BYZO_Admin_Assets` supports loading straight from the Vite dev server (`npm run dev`, `http://localhost:5173`, HMR) instead of reading `assets/admin/`'s manifest — gated by a `BYZO_DEV_MODE` constant, commented out by default in `wp-config.php` with instructions to uncomment only while actively iterating on the Vue UI in a browser, and comment back out before running the smoke test suite (which assumes built mode and fails otherwise — this bit the session that built it, see `scratchpad/smoke-admin-assets.php`'s history). `vite.config.js`'s `server: { cors: true }` is required since WordPress (a different origin) is the page loading these dev-server-served modules.
   - **Browser-verified 2026-09-02** (user screenshot): `/wp-admin/admin.php?page=bookyzo` renders the Vue app correctly — "Bookyzo" heading, "REST connectivity: connected", hash route `#/` active, Bookyzo menu item highlighted in the wp-admin sidebar with its dashicon. Full chain (Vite build → PHP manifest-read enqueue → wp.apiFetch → REST → DB) confirmed working end-to-end in a real browser, not just at the PHP/build-artifact level. Step 7 fully closed, no open gap.
8. ✅ **DONE (2026-09-02)** — Smoke tests (scratchpad CLI scripts loading `wp-load.php`, matching the sister-plugin testing convention): create a bookable item, generate slots, book one, transition its status, confirm slot capacity decrements correctly. Each step already had its own focused smoke test (steps 1-7 above); `scratchpad/smoke-phase0-e2e.php` adds the single linear story tying them together as one realistic workflow — owner creates a bookable item + sets availability (slots auto-generate immediately, not waiting for cron) → cron tick re-runs idempotently → guest browses public `/slots` → guest books via public `POST /bookings` → slot disappears from public availability → owner sees it on `GET /bookings` → owner walks it through `pending→confirmed→completed` → state machine still blocks the illegal `completed→pending` reversal → Vue admin shell enqueues cleanly. 12/12 checks passed. This script also serves as the fast regression check to re-run before every future commit, Phase 1 onward.

**Exit criteria for Phase 0: MET (2026-09-02).** A bookable item can be created, its availability set, slots generated by cron, and a booking made and status-changed — all via REST, confirmed via `scratchpad/smoke-phase0-e2e.php` plus a real logged-in browser check of the Vue admin shell (user-provided screenshot, `admin.php?page=bookyzo` rendering "REST connectivity: connected"). No UI polish yet, not on WordPress.org — that's Phase 1. **Phase 0 (Core Engine) is complete.** Next: Phase 1 — Appointment Free, the first WordPress.org release.

## Phase 1 — Appointment Free (first WordPress.org release)

Builds ON Phase 0. Nothing here should require touching the 4 core tables' schema — only UI + type-specific defaults.

**Prerequisite added (2026-09-02):** `GET/PUT /settings` (`BYZO_Settings` + `BYZO_REST_Settings_Controller`) — planned in DETAILED-SPEC.md §4 since Phase 0 but not built until now, needed for step 1's business profile form. Whitelist-validates every field (timezone against `timezone_identifiers_list()`, currency as a 3-letter code, times as H:i, numeric fields non-negative/non-zero where it matters) rather than passing PUT data through — a bad value here would silently corrupt slot-generation math downstream (buffer/advance-window fields feed directly into `BYZO_Slot_Generator`). `BYZO_Activator::maybe_seed_default_settings()` now calls `BYZO_Settings::get()` for its defaults instead of keeping a second copy, so the two can't drift. ## Free → Pro Conversion Strategy

**Principle:** every Pro feature must be something a Free user genuinely *runs into as a wall* through normal, growing use of their business — not something Claude or the plugin dangles in front of them with a lock icon. This is a hard constraint, not just good marketing: `bundle-product-plugin`'s WordPress.org submission was **rejected twice for Guideline 5 (Trialware)** specifically because it showed visible locked/disabled Pro UI in the Free plugin. See `.claude/skills/bookyzo-dev/SKILL.md` for the enforcement rules. The two goals (avoid Trialware rejection, and make Pro genuinely desirable) turn out to be the *same* goal solved the *same* way: real limits tied to real growth, discovered by hitting them, not by seeing them.

The upgrade motivation has to come from the **shape of Free's real limits**, each one a natural business-growth trigger:

| Free limit (real, not artificial) | What triggers the Free user to feel it | Why Pro's version solves it |
|---|---|---|
| One active bookable item **per type** (1 staff + 1 table + 1 event + 1 slot — all four types free, revised 2026-09-02) | Business hires a 2nd staff member, opens a 2nd table, or runs a 2nd event | Pro: unlimited bookable items per type |
| One shift per day | Business adds a lunch+dinner split, or a staff member works split shifts | Pro: multiple shifts/day |
| Basic per-type feature set (no floor plan, single ticket tier, no recurring class series) | Restaurant outgrows a flat table list, event organizer wants Early Bird + VIP pricing, studio starts a weekly class with a fixed roster | Pro: type-specific modules (B7 — floor plan, ticket tiers + QR check-in, recurring series) |
| Single location, no per-staff schedule override | Business opens a 2nd branch, or one staff member's hours differ from the shop default | Pro: multi-location + per-staff schedules |
| No deposits, one gateway | Business gets burned by no-shows on unpaid bookings, or customers ask for PayPal | Pro: deposits + multiple gateways |
| Email-only, single fixed reminder | Customers don't read email reminders and still no-show; business wants a 48h+2h double reminder | Pro: SMS/WhatsApp + multi-timing reminders |
| No customer self-service | Business gets flooded with "can I reschedule?" phone calls/emails | Pro: customer dashboard |
| No booking history/repeat-customer detection | Business wants to recognize/reward repeat customers, can't currently see who's a repeat | Pro: customer profiles + retention analytics |
| Basic count-only reporting | Business wants to know revenue by bookable item, occupancy rate, no-show trends to make staffing/pricing decisions | Pro: full analytics dashboard |
| No recurring bookings/waitlist | Business runs a weekly class or is fully booked and losing customers who'd rebook if notified | Pro: recurring series + waitlist |
| Flat price, one flat tax rate, one booking per checkout (added 2026-09-03) | Business wants to charge more in peak season, sell multiple slots in one checkout, or set a different tax rate per service | Pro: seasonal/dynamic pricing, cart checkout, per-service tax override |
| One customer login, no outside connections (added 2026-09-03) | Business's own staff need separate logins, or they want bookings to trigger something in their existing marketing/ops stack | Pro: multi-user staff logins, webhooks, marketing pixel integration |

**Practical implication for build order**: because these limits are real (not cosmetic), Free must be built with the *unlimited* version's data model in mind from day one (see `DETAILED-SPEC.md`'s repeated "don't gate the data model, gate the UI/capability" pattern) so that removing a limit in Pro is a filter override, never a schema migration or a rewrite. This is also why Phase 0 builds the full schema (multi-shift columns, etc.) even though Phase 1's UI only ever uses a subset of it.

**What NOT to do**, restated from the skill file because it's the single most expensive mistake the sister plugin made twice: never show a Pro feature as visible-but-disabled in Free with an upsell nag. If Free doesn't have a feature, it's just absent — the "wall" the user hits is a real operational need (can't add a 2nd staff member), not a UI element telling them no.
